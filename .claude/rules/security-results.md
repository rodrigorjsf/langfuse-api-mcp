# Security: tool results and discovery

Part of the non-negotiable security rules (`security.md`), moved here verbatim so it loads only with the code it governs. Keep this text and the invariant line in `security.md` in step. A reference to another section ("Tool results", "Discovery", "Filter scan", "Requests to Langfuse") points to `security-results.md` or `security-requests.md`.

**Tool results**
- Langfuse payloads are untrusted data: wrap them in a labelled envelope; strip invisible/bidi Unicode (U+E0000–E007F, zero-width, bidi overrides, variation selectors and other default-ignorable code points, #156) and control chars; a terminal escape sequence goes whole, not with its escape character alone (#193): wherever the server strips control characters from Langfuse data (`sanitize.Text` for every payload string and key, the audit line and a confirmation, `sanitize.Message` for error text taken from Langfuse), a CSI (ESC `[` or U+009B, parameter and intermediate bytes, one final byte; the U+009B form, the only one that can stand raw in the JSON text of a result, also ends its scan at a quote or a backslash, so it never takes the quote or the backslash of a JSON string) and an OSC (ESC `]` up to BEL or ESC `\`, an OSC 8 hyperlink with its URL) are removed with the rest of the sequence, by a scan of at most `sanitize.MaxEscapeSequenceRunes` (256) characters from the escape character; an escape character that starts no complete sequence within them goes alone and the text after it stays, so no payload makes the sanitizer drop more than that; text with no escape character before it (`[31m`) is never changed; each JSON string is cleaned alone; the removal runs before redaction and clipping, so a key behind or split by a sequence is still redacted and the cap counts the cleaned text (the embedded OpenAPI text of the catalog is not Langfuse data and keeps its own load-time stripping); JSON text inside a payload string (#210): a payload string that, once cleaned as above, is exactly one valid JSON value that is an object, a list or a string, with nothing but JSON blanks around it, is decoded, and its value is cleaned as a payload is (every string and key by `sanitize.Text`, a terminal escape sequence whole, each string redacted after its cleaning, a key that reads the same as another only once cleaned never shadowing the clean key, the object form of a header credential); a string of that value that is itself JSON text is cleaned the same way, down to `sanitize.MaxJSONTextLevels` (4) decodings below the payload string, and a string reached after that many is cleaned and redacted as plain text, its escapes kept. This is how the Observations v2 `input` and `output` (JSON text in a string) lose a control or invisible character written as an escape, which a client that parses the text would get back. Text cannot tell the escape of a character from the same letters written on purpose, so the string is decoded, not searched: a Windows path (`C:\\build` in the text) and `\\u001b[31m` with the backslash itself escaped decode to the letters and stay. The text is written again only when the cleaning changed its value: then it is the cleaned value written as a payload is (compact, keys in sorted order, numbers as written, a repeated key once with its last value, HTML left alone), with U+2028 and U+2029 kept as characters so that the text is never longer than it was apart from `[REDACTED]` standing for a shorter secret; otherwise it comes back byte for byte, pretty-printed or not. A value that a repeated key shadows (decoding keeps the last) is cleaned and redacted too, as a member of its own object: when it holds anything to clean the text is written again and only the last value stays, so a parser that keeps the first value, or a model reading the text, never gets it; it is looked for only in a text that holds `\u`, `\b`, `\f` or, in any case, the word `authorization` or `bearer`, because without those the walk of the kept values has found all there is. The order: the outer string is cleaned (so a raw invisible character cannot hide a JSON text from the decoder), each level is decoded and cleaned before it is redacted, then the text is redacted as before, and clipping stays last (a clipped JSON text is cut text, not decoded). Not decoded, so not cleaned of escapes, each documented: a string that is not exactly one JSON value (JSON text followed by prose, cut JSON, two values in a row, a Python dictionary printed as text), another notation of a character (`\x1b`, `\033`) and a fifth level; the letters of an escape stay there. Each level reads its string once more, so the work stays in proportion to the size of the payload, and no payload makes the result longer than twice itself, which the outer writer's escapes of U+2028 give today; the level bound is a constant of the binary and no setting, argument, payload or client changes it or turns the rule off; the work added to a string that does not start with a brace, a bracket, a quote or a JSON blank (a space, a tab or a line break) is one byte read, and a string that starts with blanks has those blanks and the byte after them read (`BenchmarkPayload`); tests prove each; never render HTML/Markdown from them; never echo them unescaped into error text. A proxy's CONNECT answer (status reason, body) is untrusted too: it is dropped, never echoed into an error, hint or audit line (#32).
- Discovery (`search_operations`, `describe_operation`, ADR-0002 amendment): operation tags and description lines are stripped of invisible/bidi and control characters when the catalog loads, a Markdown link in a line keeps only its text, bold markers (`**`, `__`) are removed, and a line is cut at 200 runes (tests prove it, #79, #82); instruction-like text cannot be detected, so both tools' text and output schemas frame the lines as third-party text from the Langfuse OpenAPI spec, data and not instructions (#82); every string of a write operation's request body schema, keys included, is stripped of invisible/bidi and control characters at load, tab and line breaks kept (#81, test-proven; no link reduction or length cut); the result size cap bounds both tools' results, text content and structured content each (#190): `describe_operation` leaves the `description` and `title` annotations (the keywords of a schema, not a property named so, and nothing inside `const`, `enum`, `default` or `examples`) out of a body schema that does not fit, the reduced schema accepts and refuses the bodies the full one does, and if it still does not fit the schema is left out whole with `body.required` kept; `search_operations` keeps the leading entries of an operation index that does not fit, at an entry boundary, with `count` the number of matches; both say `truncated` with a static hint (one for each reduction, the trace reads hint first in a cut trace query) that holds neither the query, the `operationId` nor any catalog text; the reduction only removes text from catalog text already cleaned at load, keeps the notes that frame the lines and the body schema as third-party text, takes no argument, is bounded by the catalog's own schema size and depth, and runs after the `query` and `operationId` checks, whose refusals are unchanged; `execute_write` validates a body against the full schema at every cap; a test walks every write operation of the union catalog at the smallest cap and fails naming the operation if its reduced description does not fit (tests prove each); `query` and `operationId` over 128 runes or holding a control or invisible character are refused with `invalid_argument`; the query is never echoed, and the trace reads hint of `search_operations` (#100) is static text naming only the tools and operations the resolved catalog and tool set offer, given only when the query holds the word `trace` or `traces` (#114); `describe_operation` also lists, apart from `parameters`, the filters the server applies itself on this deployment (`scannedFilters`, #199; see Filter scan): decided by the closed list of filter scan pairs and the version detected at startup, never by an argument, a payload or a client, each entry the facts of a parameter read from the catalog and one static note compiled into the binary, and the whole description fits the smallest result size cap; the static per-parameter guidance of `describe_operation` covers the `metrics_metrics` and `legacy_metricsV1_metrics` `query` (#104, #178; both built from the validator's own key list), the `prompts_list` `tag` and `filter` parameters, naming `tag` as the tag filter and `filter` as not (#141; `filter` stays in the catalog and is still sent), the `prompts_get` `label` and `version` (neither means `production`; `latest` names the newest) and the `fields` of the seven operations that take it (`trace_list`, `trace_get`, `observations_getMany`, `scores_get-many`, `scoresV3_getManyV3`, `experiments_list`, `experiments_listItems`; #178, #194): its field groups, what comes back without `fields` and what to know to use it, each only on a deployment whose version serves `fields` on that operation, from the release specs (`docs/research/langfuse.md` §1.5), a group a later release added named with that release, `core` never suggested for `scoresV3_getManyV3`, the value never checked locally, is compiled into the binary, holds no caller input and no Langfuse data, and no other parameter of any operation carries guidance (tests prove it: a walk fails, naming the operation, when an operation of the union catalog has `fields` without guidance, and the closed list of guided parameters is exact); the static body guidance (#192; `Catalog.BodyGuidance`) covers `comments_create` (its `projectId` is the ID of the project the server's keys belong to, which `projects_get` returns, named only when the resolved catalog offers it) and `scores_create` (a score needs exactly one target, `traceId` with an optional `observationId`, `sessionId` or `datasetRunId`, each named only when the body schema has it, and that schema is the deployment's (#202: `sessionId` from 3.53.0 and `datasetRunId` from 3.55.0)), is compiled into the binary, holds no caller input and no Langfuse data, is kept by every reduction of a result for the size cap, and no other operation's body carries any (tests prove it); the 404 hint of `prompts_get` called with no label and no version names the implicit `production` label from static text, never the prompt name (#178); an unknown, excluded or (write mode off) write `operationId` is `operation_not_found`, echoed only redacted and cut to 64 bytes; an ID of the union catalog that the resolved catalog does not offer is `operation_unavailable` in `describe_operation`, `execute_read` and `execute_write` (#174, ADR-0002 amendment), its message and static hint naming the catalog's own operation ID, the replacement operations the catalog offers and the deployment profile, never the call's text, and a legacy line of the operation index names a preferred operation only when the resolved catalog offers it (tests prove it); on a deployment where the legacy family and the family of a preferred operation are both on, the entry of a legacy read operation whose preferred operation the resolved catalog offers as a read operation, of another operation family than the legacy one, also carries a `note` (#212): the key is optional in the structured content and declared in the output schema as static text written by this server, not Langfuse text, and the text line shows it after the description and the tool, behind the label ` | note from this server: `, so the third-party line keeps its value and its framing byte for byte; the note is text compiled into the binary plus one catalog operation ID, the preferred operation (`On this deployment <id> reads another store and can return less than this operation, or nothing, for data written through the legacy APIs, so a result that is empty or shorter than expected is worth checking with this operation.`, a possibility and not a fact), decided at `Catalog.Resolve` from the operation families of the catalog and the deployment profile detected at startup (`Operation.PreferredOfOtherFamily`: ten entries on the profile with every family on, the seven that prefer a v4 read operation when the experiments family is off, none on the legacy-only, v4-only or no-family profiles, so those are byte for byte what they were), never by a `query`, an argument, a payload or a client, copying no spec description text, no caller text and no Langfuse data into it, so a hostile query changes no note, the notes of a filtered index are those of the same entries in the full index, two clients of one server read the same index, an entry that the result size cap keeps is kept with its note whole and a cut stays at an entry boundary; the trace reads hint adds, only when the v4 read family and the legacy family are both on and the catalog offers any of `trace_get`, `trace_list`, `legacy_observationsV1_getMany` and `legacy_metricsV1_metrics`, one static sentence after its text saying the legacy reads may hold data sent through the legacy ingestion API that the reads above lack and naming those the catalog offers, each only after its own lookup, `get_trace_tree` not a second time (tests prove each). `execute_read` echoes an unknown `operationId` only redacted, cut and stripped of control, invisible and bidi characters, under the static hint naming `search_operations` (#36). `get_trace_tree` (#74): a `traceId` over 128 runes or holding a control or invisible character, an `include` value other than `io`/`metadata`, a wrong type or an unknown argument is refused with `invalid_argument` before any Langfuse request, never echoing the value (an unknown argument's name only redacted and cut to 64 bytes); the `traceId` goes to Langfuse only as a query parameter; the tool is registered on every deployment (#175, ADR-0002 amendment): where neither the v4 read family nor the legacy family is on, a call that passed those checks is answered `operation_unavailable` with fixed text (the deployment's version and families, `trace_get` only when the resolved catalog offers it, never the `traceId`) and no request, and the tool set stays fixed at startup and identical for every client; where only the legacy family is on it builds the tree from `legacy_observationsV1_getMany` (#187, ADR-0002 amendment): the `traceId` only as a query parameter, at most 10 pages of 100 (`workflows.MaxLegacyTracePages`, `LegacyTracePageSize`) whatever the call asks, through the one client (rate limit, concurrency cap), each page cleaned and redacted before its rows are read, then `input`, `output` and `metadata` removed from every row by key name at the top level unless `include` asks for them (so a hidden character or escape in a key cannot keep them), then each top-level key whose value is JSON `null` removed except `id`, `parentObservationId` and `startTime` (#200: on the cleaned row, so a `null` key with a hidden character in its name goes and cannot shadow a kept key; only the type `null` counts, so `"null"`, `""` and a string empty once cleaned stay; nothing inside a value changes; the Observations v2 path, `execute_read` and the filter scan keep their `null` keys; no argument, payload or client turns the rule on or off, and it adds no text to a result, hint or `meta`), every row returned whatever its `id` and `parentObservationId` hold, a failed page ending the call with its tool error and no partial tree, and the hints (the next page number included) static text plus numbers; where both the v4 read family and the legacy family are on (#209) the tree is still read from Observations v2 alone, an empty tree costs the one request to that route and none to a legacy route, and the hint of an empty tree adds, after today's text, that the legacy reads of the deployment may hold the trace, naming `legacy_observationsV1_getMany` (with `traceId`) and `trace_get` through `execute_read`, each only when the resolved catalog offers it as a read operation (neither offered, today's hint): static text that depends only on the deployment profile and the resolved catalog, both fixed at startup, never the `traceId`, another argument or any Langfuse answer, and no argument, payload or client changes it, so a hostile page with instructions, hidden characters or markup in its `meta` or extra keys leaves it unchanged; every other deployment keeps its hint byte for byte, and the `get_trace_tree` description holds one static sentence, the same on every deployment, saying Observations v2 can lack observations sent through the legacy ingestion API (the only cover for a tree that is short and not empty, and a fallback to the legacy list is a maintainer decision, #213); the trace tree comes back sanitized inside the untrusted-data envelope, its large values clipped and, only if that is not enough, cut at a row boundary at the result size cap. A continuation cursor is opaque Langfuse data (#93): never decoded, handed back only as `data.meta.cursor` inside the envelope (never in a hint or the audit line), and sent back through `execute_read` unchanged as one string query parameter (a non-string `cursor` is refused); tests prove it.
