# Hybrid tool surface: search + split execute + dedicated workflow tools

The Langfuse public API has ~100 in-scope operations; one tool per operation would spend thousands of context tokens every turn, and a single `execute` tool cannot carry truthful `readOnlyHint`/`destructiveHint` annotations and is the open-ended tool OWASP LLM06 (Excessive Agency) says to narrow. So the server exposes: `search_operations` (catalog lookup), `execute_read` (GET operations only, `readOnlyHint: true`), `execute_write` (mutating operations only, `destructiveHint: true`, see ADR-0003), and a small set of dedicated read tools for the highest-traffic workflows (trace investigation, error/latency/cost triage).

## Consequences

- Every operation stays reachable; the catalog is generated from `internal/catalog/spec/langfuse-openapi.json`, so "implements all endpoints" is a testable property (catalog ⊇ in-scope operations, see ADR-0004).
- Satisfies the Anthropic connector review criterion that read and write live in separate tools.
- `execute_*` accepts operation IDs from the catalog only — never a free-form URL or path.

## Amendment: operation discovery in two tools (2026-09-26, M3 grilling)

`search_operations` is split into two read-only, closed-world tools, so an agent — including a small model that does not know the Langfuse API — can find and call any operation using only this server:

- `search_operations` returns the **operation index**: one line per catalog operation (`operationId` — first line of its description; for a deprecated operation, the line saying what it does plus "legacy: prefer <replacement> when it is available", which the union catalog carries as `x-summary`, instead of the ~500-character deprecation notice, #79), grouped by OpenAPI tag, v4 family before legacy (ADR-0012 §5). An optional `query` keeps only operations where every whitespace-separated term appears, case-insensitively, in the `operationId`, the tag or that first line. No match is a normal result that names the tags and says to call again without `query`; the query is never echoed. The result carries text plus `structuredContent` under an `outputSchema`.
- `describe_operation` takes one `operationId` and returns its **operation description**: every parameter with location, type, required flag, enum and bounds, from the catalog's own schema.
- Write operations are left out of both unless write mode is on; then each index line says which tool runs it. Results come from the same catalog `execute_read` uses; filtering by the deployment profile lands with the version-aware catalog (ADR-0012), and until then a listed operation the deployment lacks answers `operation_unavailable`.
- `execute_read` hints point here: `operation_not_found` names `search_operations` (#36); `invalid_parameter` lists the operation's valid parameter names and names `describe_operation`.
- The `query` is model input: bounded (128 runes), refused with `invalid_argument` when it holds a control or invisible character, never echoed. Descriptions are third-party text fixed at build time: sanitized (invisible, bidi and control characters stripped; Markdown links and `**`/`__` bold markers reduced to their text, #79, #82), framed in both tools' output as third-party text read as data and not instructions (#82: instruction-like text cannot be detected reliably) and reviewed in the spec-regeneration diff, not wrapped in the untrusted-data envelope; a test asserts the index holds no forbidden character.

Rejected: **semantic search over embeddings** — an external embedding API breaks local-first (ADR-0005), a bundled model is a heavy dependency, it adds vector/embedding risk (LLM08:2025 / LLM09:2026), and the read index of the unresolved union catalog is about 7 KB of text, ~1.8k tokens (68 GET operations, measured 7,081 bytes, the #82 third-party note included, by `TestSearchOperationsWithoutQueryListsTheReadIndexWithinItsBudget`, which caps it at 8 KiB = 8,192 bytes, a 1,111-byte margin of about 10 new read operations at the current ~104-byte average line, #87; about 14 KB for all 123 in write mode, #79; the earlier ~1.2k-token figure counted 58 operations of a single spec), small enough for the calling model to match intent itself. **A skill as the primary discovery path** — the server cannot make a client load a skill, and a static skill cannot know which operations the connected deployment serves (ADR-0012); skills stay the workflow layer of M6 and may point to `search_operations`. **One tool with a search mode and a detail mode** — mutually exclusive arguments are what small models mix up; the second tool costs ~150 tokens of definition.

Evidence that small models benefit comes from a scripted eval in `scripts/` (about 10 natural-language intents; Haiku 4.5 must reach the right `operationId` and parameters through these tools alone), run by hand at the end of M3 and again in M6, its result recorded in the PR — not a CI gate.

## Amendment: M3 ships one workflow tool, `get_trace_tree` (2026-09-26, M3 grilling)

M3 ships a single workflow tool, the trace tree. Error, latency and cost triage are deferred: they are mostly a choice of filters and a reading of Metrics v2, which an M6 skill can teach over `execute_read`, and they come back only if the small-model eval shows agents fail at them. The payload-query guard (#42) moves with them.

`get_trace_tree` is registered only when the v4 read family answers (ADR-0012 §6; superseded by the amendment of 2026-10-10 below, which registers it on every deployment):

- Input: `traceId` (1–128 runes; control or invisible characters refused with `invalid_argument`; sent as a query parameter, never echoed unbounded) and an optional `include`, a closed subset of `["io","metadata"]`. Unknown arguments are refused.
- It calls `observations_getMany` with `traceId`, `limit=1000` and field groups `core,basic,time,usage,model,metrics`, plus `io`/`metadata` only when asked; it follows `meta.cursor` for at most 5 pages. Past that, the result is marked truncated and returns the cursor, with a hint to continue through `execute_read`.
- Output: a flat list in depth-first pre-order with `depth` and `parentObservationId`, siblings by `startTime` ascending, so the row truncation of the untrusted-data envelope applies at the result size cap (100 KiB when this was written; 64 KiB by default and configurable since M8, with value clipping before any row is left out, see the amendment below). An observation whose parent is absent becomes an extra root with `orphan: true`; several roots are ordered by `startTime`. A trace with no observations is an empty result with a hint, not `langfuse_not_found`, because Observations v2 cannot tell "missing" from "not yet ingested".
- No scores: the agent reads them with `execute_read` `scoresV3_getManyV3`.
- The payload is wrapped and sanitized like any `execute_read` result; the audit line names `get_trace_tree` and counts the Langfuse requests it made.

## Amendment: `get_trace_tree` is registered on every deployment (2026-10-10, M8 grilling)

`get_trace_tree` on every deployment shipped in M8 (#175), and so did `operation_unavailable` for a filtered operation (#174). The user skill and the tool reference name `get_trace_tree`; on a deployment without the v4 read family the tool was not registered, so an agent that called it was refused by its host before the server could say anything (campaign finding M2). The tool is now registered on every deployment. Where neither the v4 read family nor the legacy family is on it answers the tool error `operation_unavailable`, with a hint naming the deployment's version and the operation that reads one trace there, when the catalog offers one; where only the legacy family is on it builds the trace tree from the legacy observations list (the amendment below, #187; #175 first answered `operation_unavailable` there too). The tool set is the same on every deployment and still fixed at startup.

A trace tree over the result size cap keeps every observation: its largest string values (the inputs and outputs) are clipped first, and rows are left out at a row boundary only when clipping every value to the floor is not enough (#177; this refines the row truncation described above).

Building the trace tree from the legacy observations list was first deferred, because that list has no field selection and always carries input and output; the amendment below builds it, and removes those fields on the server.

In the same milestone, an operation ID that is in the union catalog but filtered out by the deployment profile is answered `operation_unavailable` by `describe_operation`, `execute_read` and `execute_write`, with the operation that replaces it on this deployment, instead of `operation_not_found`; a legacy line of the operation index names a preferred operation only when the deployment offers it; and the trace reads hint of `search_operations` also exists on a legacy deployment. A write operation ID while write mode is off stays `operation_not_found`.

## Amendment: `get_trace_tree` builds the trace tree from the legacy observations list where only the legacy family answers (2026-10-10, M8, #187)

The campaign on Langfuse 3.80.0 ([record](../research/raw/2026-10-10-e2e-langfuse-3.80.0.md), findings H3 and M2) showed what a v3 deployment costs an agent without a trace tree: it reads the trace with `trace_get`, rebuilds the nesting from parent IDs itself, and a large trace could not be read at all. The maintainer decided on 2026-10-10 to build the tree there, which settles the question the first amendment of that date left open ("build it, or record that v3 deployments read one trace through the single-trace operation").

Decision:

- **Source.** Where the v4 read family is off and the legacy family is on (Langfuse v3, or v4 in a legacy mode), `get_trace_tree` reads the legacy observations list, `legacy_observationsV1_getMany` (`GET /api/public/observations`), with the `traceId` filter, which every release since 3.0.0 serves. Where the v4 read family is on, whatever the legacy family's state, it reads Observations v2 as before. Where neither family is on it answers `operation_unavailable` as the amendment above says. The choice is made once, from the deployment profile detected at startup.
- **Rejected source: the single-trace operation.** `trace_get` (`GET /api/public/traces/{traceId}`) returns the whole trace in one response, so a trace larger than the response read cap (5 MiB) cannot be read at all, and it cannot be paged.
- **Bounds.** The legacy list pages by `page` and caps `limit` at 100. The tree reads page 1, 2, … at a page size of 100 and stops at the last page (the page `meta.totalPages` names; without it, at the first empty page, because a short page may be a smaller page size) or after 10 pages: 1,000 observations, 10 requests. No argument changes either number. On Observations v2 the bound stays 5 pages of 1,000.
- **Shape.** The envelope and the ordering are the same on both paths: a flat list in depth-first pre-order, each row with `depth` and `parentObservationId`, siblings and roots by `startTime` ascending, an observation whose parent is absent as an extra root with `orphan: true`, and `meta` with the observation count and `truncated`. The fields inside a row are the ones that deployment's Langfuse returns, not translated (no name, value or unit changes), so they differ between the paths (the legacy list returns an observation's `latency` in milliseconds, Observations v2 in seconds); besides the removal of `input`, `output` and `metadata` unless `include` asks, the one change to a legacy row is leaving out the keys Langfuse sent as `null` (the amendment of 2026-10-11, #200, below). The tool keeps one static description for every deployment that says so.
- **Input, output and metadata.** The legacy list has no field selection and always returns `input`, `output` and `metadata`. The server removes those keys from every row, by name at the top level of the row and after the page has been cleaned, unless `include` asks for them, so the default result carries none of the three (a legacy row stays wider than a v4 row; see the consequences). The bytes are still read from Langfuse; with `include` they are returned, and value clipping (#177) keeps the result inside the result size cap.
- **Truncation.** When pages remain, the result says `truncated` and a static hint names `legacy_observationsV1_getMany`, the `traceId` parameter and the number of the next page, through `execute_read`. A page that fails, a page over the response read cap included, ends the call with the tool error of that failure: no partial tree is returned as if it were whole.
- **Discovery.** The trace reads hint of `search_operations` on a deployment where only the legacy family answers names `get_trace_tree`.

Considered and rejected: `trace_get` as the source (above); leaving the tree to the agent on v3 (the campaign cost); translating legacy rows into the Observations v2 shape (it would invent fields the deployment does not return, and hide the latency unit).

Consequences: the workflow module now has two readers over one ordering; a legacy-family tree costs up to 10 requests instead of 5, inside the shared rate limit and concurrency cap and counted in the audit line (tool `get_trace_tree`, operation `legacy_observationsV1_getMany`); the row fields of the tree depend on the deployment, and agents read the units from the tool description; a legacy row is about 870 bytes as Langfuse sends it, even without input, output and metadata (39 keys, most null), which would let about 75 observations fit the default result size cap; the amendment of 2026-10-11 (#200) below leaves the null keys out, and a longer trace is still cut at a row boundary, which `meta.observations` and the hint make visible. ADR-0012 §6 points here.

## Amendment: the trace tree built from the legacy list leaves out the keys Langfuse sent as `null` (2026-10-11, M8, #200)

#187 left a legacy trace tree of more than about 75 observations cut at the default result size cap with no large value to clip: a row of the legacy observations list has 39 keys on Langfuse 3.80.0, most of them `null` for an observation with no model, usage or cost, and is about 870 bytes. The outcome was decided already (the spec's story 53 and the criterion of #187 that a trace over the cap keeps every observation, with only large values clipped); this amendment picks the means.

Decision:

- **The rule.** From every row of a trace tree built from the legacy observations list, the server removes each top-level key whose value is JSON `null`. An absent key means Langfuse returned `null` for it. The tool description says so.
- **Three keys stay.** `id`, `parentObservationId` and `startTime` are kept whatever they hold: the tree is built from them, and the tool promises `parentObservationId` on every row, which is `null` for a root. `depth` and `orphan` are written by the server after the rule and are not touched.
- **Only `null`, only the top level.** A key that holds `0`, `false`, `""`, `{}`, `[]` or the text `"null"` stays. Nothing inside a value changes: with `include`, what `input`, `output` and `metadata` hold comes back as Langfuse sent it, cleaned, and a top-level `input`, `output` or `metadata` that is `null` goes like any other key.
- **When and where.** After a page is cleaned and redacted, as the removal of `input`, `output` and `metadata` is, so a key is matched by the name and the value the agent would read (a `null` key written with a hidden character, a bidi character or a JSON escape goes like any other, and cannot shadow a kept key); before the ordering is written and before the result size cap. The ordering does not change. The legacy path only: Observations v2 rows, `execute_read` with `legacy_observationsV1_getMany` and the filter scan return what Langfuse returned, `null` keys included.
- **Not the rejected translation.** The first amendment of 2026-10-10 rejected translating legacy rows into the Observations v2 shape because it would invent fields the deployment does not return and hide the latency unit. This rule invents no field, renames none and converts no value or unit (`latency` stays in milliseconds on this path); what is lost is the difference between `null` and absent, and the description says how to read it. What the amendment of #187 says about the rows, that they are not translated, stays true for names, values and units.
- **Rejected: an allow-list of keys.** It is the subset the first amendment rejected: the server would choose which fields of the deployment an agent may see, and the list would need checking against every release. Also not added: dropping empty or zero values, or a larger default result size cap (it applies to every tool result, #176).
- **Measured, not promised.** A row of the legacy list recorded from the pinned 3.80.0 for a span with no model, usage or cost (`internal/server/testdata/legacy-observation-3.80.0.json`, 865 bytes, 39 keys, 18 of them `null`) is 527 bytes in the result once the rule, the removal of `input`, `output` and `metadata` and the `depth` key are applied. At the default result size cap (64 KiB) 124 such observations fit whole, and of 130 the tree returns 123 rows marked truncated, against 78 before the rule. The 130-observation trace of the live test, whose spans carry no end time and so have more `null` keys, returns 125 of 130 rows on 3.80.0 (76 before). So 130 do not fit, and the ticket is complete: the result says `truncated`, `meta.observations` counts the rows read and the hint says how many were kept. A tree of 1,000 observations, the reading bound, does not fit 64 KiB under any option here; the remedies are the same: the operator raises `LANGFUSE_MCP_MAX_RESULT_BYTES`, or the agent pages through `execute_read`.

Consequences: a legacy row an agent reads is smaller by its `null` keys; a field absent from it means `null` (the description says so, and so does `docs/reference/tools.md`); the tool description grows by one sentence and stays one static text for every deployment; no argument, payload or client turns the rule on or off or changes the kept keys; the readers of the two paths still share one ordering and one result size cap.
