# Handoff — #80: execute_read does not enforce spec-given parameter bounds that describe_operation reports

## What was built
`Operation.Request` (so `execute_read`) now refuses a value outside the bounds a parameter's spec gives, before any request: `minimum`/`maximum` for `integer`/`number`, `minLength`/`maxLength` counted in runes for `string`, item bounds for a repeated parameter. The refusal wraps `ErrInvalidParameter` (server: `invalid_argument`, generic parameters hint naming `describe_operation`) and reads e.g. `parameter s: want a length from 2 to 4 characters` / `parameter n: want a value from 0 to 1000` / `parameter tags: item 1: want a length of at most 3 characters` — the bound, never the value. The check runs after the list `limit` check, so `limit` keeps `ErrLimitOutOfRange` and its paging hint. Neither the embedded union catalog nor today's release specs carry any such bound, so the change is latent for real operations.

## Acceptance criteria
- [x] Out-of-bound value refused with `invalid_argument`, naming parameter and bound, never the value — `TestAValueOutsideASpecGivenBoundIsRefusedNamingTheParameterAndTheBound` (catalog seam; server mapping of `ErrInvalidParameter` to `invalid_argument` with no request is existing behaviour, `TestExecuteReadRejectsInvalidParametersNamingTheFieldAndTheReason`). Real bounds from #71: none exist (jq over the union catalog returns 0).
- [x] `limit` refusal keeps its own hint — `TestALimitOutsideOneToTheCapIsRefusedWithAHintWithoutCallingLangfuse` (server, unchanged, green) and `TestAListLimitOutsideTheCapKeepsItsOwnRefusalWhenTheSpecBoundsItToo` (limit 1001 against a spec max 1000 still yields `ErrLimitOutOfRange`).
- [x] Dangerous parameters: min−1/min/max/max+1, multi-byte string at and one rune over the limit, wrong type, 1 MiB string, list items — table cases in the bound test; `FuzzRequestEnforcesALengthBoundWithoutRepeatingTheValue` (accepts only 2..4 runes, refusal is one fixed string).
- [x] Prompt injection: instructions, bidi, control characters, markup never appear in the refusal — `TestTheRefusalOfAnOutOfBoundValueNeverRepeatsTheValue`; the audit line sets no `cause` on an invalid-parameter refusal (`internal/server/server.go:276-279`), so it cannot carry the value.

- A parse failure in the numeric check fails closed (unreachable).
