## Decisions & deviations
- The interrupted earlier attempt left `181-partial.patch`. I reused its code and docs, but re-derived red (hint test failing on base `server.go`) and re-ran every live deployment myself; I corrected claims it made that no test or measurement backed (an events_only message quoted verbatim, "a dataset with no folders behaves the same", "about 6 s" for `dual`, which measured 8.1 s).
- 4.46.0 `events_only`: the ticket asks to assert the runs belong to the dataset on every pin, but that profile has the legacy family off, so no runs can be read. The test asserts `operation_unavailable` from HTTP 404 instead and the research note says why. The live test session runs under an unknown profile (all families on), so the request reaches Langfuse; the shipped server would refuse earlier, per `internal/catalog/resolve_test.go` ("4.x events_only"). Flag in the PR body.
- `datasets_deleteRun` is proven only by a direct `DELETE` of the shared route (200 on the three serving pins, 404 on events_only), not through `execute_write`: `execute_write` cycles live-run on 4.46.0 only (`write_integration_test.go`). The docs say exactly that. The statement about `datasets_deleteRun` was part of the removed claim, hence the direct check.
- Run items are listed late: `datasets_getRun` returned the run item after 6.1 s on 3.225.11 and 8.1 s on `dual`, at once on 3.80.0. The test polls up to 90 s. Not compared with a folder-less dataset, so not claimed to be Folder-name related.
- `POST /dataset-run-items` accepted a random `traceId` no trace carries, on every pin, so the test seeds no trace.
- The public API has no dataset delete: datasets stay (unique names) in the throwaway project.
- The CI workflow needed no change: the new tests self-skip by deployment, and the 3.x skip list already covers the unrelated v4-only tests. Running the whole integration suite on 3.80.0 without that skip list fails three older tests (`observations_getMany`, prompt delete 405); that is the existing CI skip list, not new.
