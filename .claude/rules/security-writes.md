# Security: write gating

Part of the non-negotiable security rules (`security.md`), moved here verbatim so it loads only with the code it governs. Keep this text and the invariant line in `security.md` in step. A reference to another section ("Tool results", "Discovery", "Filter scan", "Requests to Langfuse") points to `security-results.md` or `security-requests.md`.

**Write gating**
- `execute_write` (#110): an excluded, unknown or read `operationId` is `operation_not_found` (an unavailable `operationId`, #174, is `operation_unavailable` in every tool that takes one, whatever kind of operation the tool runs: `execute_write` says it of an unavailable read operation and, in write mode, `execute_read` of an unavailable write operation; a write operation ID while write mode is off stays `operation_not_found`), echoed only redacted and cut to 64 bytes; path and query parameters get the `execute_read` checks; the body must be a JSON object where the schema expects one (a JSON object or a list where it takes either, the one score or list of scores of `scores_create` from Langfuse 4.55.0, #225; every item is then checked against the score schema, the refusal naming the item's index), at most 256 KiB compacted and 32 levels deep, and absent where the operation takes none, refused with `invalid_argument` naming the rule, never the value, before any request; then (#112) it is validated against the operation's JSON Schema 2020-12 for the deployment's version (#202, below), compiled once, and a failure is refused with `invalid_argument` naming only the JSON location (built from schema property names and array indexes, never a caller's key) and the failed keyword, never a value; unknown keys are refused where the schema forbids them. The body is the one of the version detected at startup (#202, ADR-0012 amendment): the union catalog keeps every distinct body the release specs gave the operation, each with the releases it holds for (`x-request-bodies` with `x-spans`; an operation the server never offers, ADR-0004, keeps its newest body only, `x-newest-body-only`, and load fails if an operation the server offers is marked so), `catalog.Resolve` picks the body of the newest release not newer than the deployment (the newest when no version was detected), and `describe_operation` returns it and `execute_write` checks against it, in full at every cap; nothing a Langfuse answer says, no argument and no client selects a body, so two clients of one server get the same schema; a refusal names the JSON location from that schema's own property names, never a caller's key or value, its hint names no release, and a property only another release has is an unknown key where this schema lacks it; the size, depth, object, absent-body checks and the confirmation come first and are unchanged under every body; only the bodies a version chooses are compiled, a schema that does not compile stops startup (`Catalog.BodyError`) and a body is never checked against it; every stored body, the older ones too, is stripped at load, compiles, has no property named like a credential and, reduced, fits the smallest result size cap. In write mode `describe_operation` returns the body schema (stripped at load, framed as third-party text), a `destructive` flag and, for `comments_create` and `scores_create` only, a static `body.guidance` (#192), and `search_operations` gives every write line its HTTP method and `destructive`, the value `describe_operation` returns (#192). Every destructive operation (DELETE, PUT, PATCH) runs only after the user confirms that exact call (#113, ADR-0003 amendment): after its parameter and body checks, the server asks through form elicitation with a multi round-trip request (`InputRequests` + a `RequestState`; older-protocol clients go through the SDK middleware, same handler path). The state is `<expiryUnix>.` + base64url(HMAC-SHA256(key, `<expiryUnix>|<operationId>|` + the checked request re-encoded deterministically)), the key 32 `crypto/rand` bytes drawn at startup, never logged or persisted; it expires after 5 minutes and is compared with `hmac.Equal`. Fail-closed, nothing sent: no form elicitation (per-request capabilities) → `confirmation_unavailable`; decline or cancel → `confirmation_declined`; an accept without a valid state (sent on the first call, other arguments, forged, corrupted, expired, another process's key) → `confirmation_invalid`. No setting skips it. The confirmation text names the operation ID, method, path and query parameters and a body summary cut at 300 runes (saying so, with the body size in bytes), the trace ID count for `trace_deleteMultiple`; every argument-derived string is stripped of control, invisible and bidi characters, redacted and shown quoted, markup as text (not escaped: the elicitation message is plain text per MCP, so markup rendering is the client's). Replay of the identical call within the expiry is not prevented (every confirmed method is idempotent). POST creates run without a server confirmation. A write is never retried. Its audit line is logged at `Warn` with `confirmation` and never the body. Excluded from the catalog: `media_getUploadUrl`, `media_patch`, `llmConnections_upsert`, `blobStorageIntegrations_upsertBlobStorageIntegration`; a catalog test fails on any property whose name contains `secret`, `password` or `accessKey` in any stored body of an in-scope write operation, whatever release it is from (ADR-0004 amendment). Tests prove each.
