# Security: redaction

Part of the non-negotiable security rules (`security.md`), moved here verbatim so it loads only with the code it governs. Keep this text and the invariant line in `security.md` in step. A reference to another section ("Tool results", "Discovery", "Filter scan", "Requests to Langfuse") points to `security-results.md` or `security-requests.md`.

**Credentials**
- Langfuse keys, where a key starts (#208, #210, #211): the key characters (`A-Za-z0-9_-`) after `pk-lf-`/`sk-lf-` are replaced by `[REDACTED]` when the prefix stands at a word boundary, directly after a JSON escape written as text, directly after a place where the cleaning removed something, or, for a generated key, wherever it stands. A generated key (#211) is `pk-lf-` or `sk-lf-` followed by a UUID (8, 4, 4, 4 and 12 hexadecimal digits with hyphens, either case): it is replaced wherever it stands, with every key character after the UUID, and what stands before the prefix is kept (`xsk-lf-<uuid>` comes back as `x[REDACTED]`, `KEY_sk-lf-<uuid>` as `KEY_[REDACTED]`). It is the shape Langfuse itself generates (the prefix and `randomUUID()`), so it is the key a trace is most likely to hold, and no word or slug has it, so it needs no boundary. Costs, accepted: a name that really is a word ending in `sk` or `pk`, then `-lf-` and a UUID (`task-lf-<uuid>`) is redacted from the prefix on (`ta[REDACTED]`); a key that is no UUID keeps the rules below. The escape: one or more backslashes, then `b`, `f`, `n`, `r` or `t`, or `u` and four hexadecimal digits. That is how a line feed reads inside a string that holds JSON text (the Observations v2 `input` and `output`, stringified once or more: one backslash and `n`, two, four), where the letter of the escape is a word character and no boundary stands before the key. The escape stays character for character, so a string that held valid JSON text still does, decoding to the same value with the key replaced. The rule on text reads the text only and is compiled into the binary: it decodes nothing and counts no backslashes, so a literal backslash and a letter before a key (`C:\nsk-lf-…`, or an escaped backslash and `nsk-lf-…`) is taken for an escape too, an over-redaction accepted; no payload, argument, parameter, Langfuse answer or client changes it or turns it off. The same pattern serves every place a key is redacted (payload strings and keys, Langfuse error text, the names an error echoes, the confirmation text, the audit line, the last pass over a result), always before a cut; a text without `k-lf-` skips it. The removed place (#210): wherever the redactor cleans a text itself (`Redactor.Redact`, `sanitize.Payload`), a place where `sanitize.Text` removed an invisible, bidirectional or control character, or a whole terminal escape sequence, is a boundary of its own, whatever stands before it (`textPlaces` records the places, `redactAfterPlaces` reads them, for the key and for the header keywords below): `token`, a zero-width space and `sk-lf-…` come back as `token[REDACTED]`, `x`, a bell and `sk-lf-…` as `x[REDACTED]`, and a word split right before the prefix by a hidden character (`ta`, a zero-width space and `sk-lf-name`) is redacted too, an over-redaction accepted; `task-lf-name`, where nothing was removed, stays; a key that a place splits is found whole, as before (the text is cleaned first). Inside a string that holds JSON text (below, "Tool results") the strings are decoded first, so the escape of a character the cleaning removes (`x\bsk-lf-…`, `x\u200bsk-lf-…`, `x\u001b[31msk-lf-…`) is a removed place too, and a key split by such an escape (`sk-lf-abc\u200bdef-…`) is redacted whole; the escape of an ASCII letter, digit or underscore before a key (`x\u0041sk-lf-…`) would glue the key to a decoded letter, so `redactKeysAfterLetterEscapes` redacts it in the text before it is decoded, the escape kept while the text is not written again. The confirmation text and the audit line read a text where something is dropped after the redactor used to read it, so they take the same places (#211): the body summary of a confirmation drops the tab, line feed and carriage return of every string (`sanitize.LineValue`, with `linePlaces` recording where), and the place of such a character is a boundary like any removed place (`word`, a line feed and `sk-lf-…` come back as `word[REDACTED]`, `Bearer <token>` after it as `wordBearer [REDACTED]`), while a credential the dropped character splits is found whole (the line is cleaned first); a tab is a blank of the header rule and the summary drops it, so the place of a dropped tab is read as the blank it was, by the header patterns themselves on the text with a space put back there: the run of token characters that starts at the place is replaced whole, whatever else was dropped inside it, when it has 16 characters and a header ends in its scheme right before the place (`Bearer`, a tab and `<token>` come back as `Bearer[REDACTED]`, `Authorization: Basic`, a tab and `<token>` as `Authorization: Basic[REDACTED]`, the quoted text form the same, and under an `Authorization` name of the body `{"Authorization": "Basic[REDACTED]"}`, a list item included); only the 128 bytes before the place are read (`maxBlankReach`, the bound that keeps the work per place constant), a line feed or carriage return is no blank of the token rule and changes nothing, and a shorter token, a keyword glued to a letter and a scheme under another name stay; the operation ID of the audit line is redacted by the redactor, which cleans the text itself and sees the place, before `sanitize.Text` drops what is left. Not redacted, each a case of its own and documented: a key that is no UUID glued to an ASCII letter, digit or underscore that is really there (`xsk-lf-abc123`, `KEY_sk-lf-abc123`, `1pk-lf-abc123`: a key the operator set through headless initialization or the admin API, or a test key; a word that only holds the prefix, `task-lf-name` or `task-lf-normalize-all-inputs`, stays as it is, and so does a prefix followed by a UUID one digit short, by a letter that is not hexadecimal or by 32 hexadecimal digits with no hyphen); dropping the boundary for every key shape would close it and redact those words (Langfuse's own log masking has no boundary), and that is a maintainer choice, not a change to make unasked. In text that is not decoded (a string that is not exactly one JSON value, another notation of a character such as `\x1b`, a fifth level of JSON text), a key split by a control or invisible character written as an escape, which is redacted only up to the escape: the text of the escape and the rest of the key stay. Tests prove each.
- Header credentials inside Langfuse data (#180, #196): the token of a credential under an `Authorization` name or after `Bearer` is replaced by `[REDACTED]` and the scheme stays (`Authorization: Bearer [REDACTED]`, `{"Authorization": "Basic [REDACTED]"}`). A scheme is a letter, then letters, digits and `_ . + -`. A token is a run of at least 16 printable ASCII characters other than space, `"`, `'`, `` ` `` and `\` (`minTokenLength`, kept above the 10 characters of `[REDACTED]` so redacting twice changes nothing); it ends at the first other character, so a closing quote or a JSON escape ends it, and a credential holding such a character (or a non-ASCII one) is redacted only up to it, if that part has 16 characters. One name rule, compiled into the binary and never changed by a payload or an argument, serves every form (`isAuthorizationName` for the object form, the patterns of the other two encode the same rule, and the tests walk one list of names through all three): a name counts when, with invisible and control characters stripped, surrounding blanks dropped and case ignored, it is `authorization` or ends in `authorization` after a character that is not an ASCII letter or digit (`Authorization`, `Proxy-Authorization`, `X-Upstream-Authorization`, `http.request.header.authorization`, `HTTP_AUTHORIZATION`); a name that only contains the word (`authorizationMode`, `authorization_url`, `reauthorization`) does not. Three forms: (1) the plain form `<name>: <scheme> <token>`, blanks (spaces or tabs) around the colon and at least one before the token, and `Bearer <token>` anywhere, `bearer` in any case at the start of a word; the name of the plain form, and `Bearer`, also start directly after an escape written as text (#211: the escapes of the key rule, `wordEndedEscape`, one rule for both, so `x\nBearer <token>`, a backslash and `n`, is redacted, the escape, the keyword and the scheme kept and only the token replaced, and `C:\nBearer <token>` too, an over-redaction accepted) and directly after a place where the cleaning removed something (`x`, a zero-width space and `Bearer <token>` come back as `xBearer [REDACTED]`; `re`, a zero-width space and `authorization: Basic <token>` as `reauthorization: Basic [REDACTED]`, an over-redaction accepted, the same trade as for the key; the token of an earlier credential runs up to the next blank, so it swallows a keyword that the removed character glued to it, and a keyword that starts within 64 bytes after the place, in the same run of token characters, is a start even there: directly (`Bearer <token>`, a zero-width space and `Bearer <token>` come back as `Bearer [REDACTED] [REDACTED]`), or after a header name glued to it (`Authorization: Basic <token>`, a bell and `Proxy-Authorization: Basic <token>` come back as `Authorization: Basic [REDACTED] Basic [REDACTED]`; `maxKeywordReach`, the bound that keeps the work per place constant); a credential found at a place swallows such a keyword the same way and the token after it is still replaced (`x`, a zero-width space, `sk-lf-abc123`, a zero-width space and `Bearer <token>` come back as `x[REDACTED] [REDACTED]`, and two `Bearer <token>`, each after a place, as `xBearer [REDACTED] [REDACTED]`); a name that puts the word farther than that from the place is the pattern's business and stays); wherever nothing was removed the headers are read before the keys (`Redactor.redact`), because a key takes every key character after its prefix, a hyphen and the letters of a keyword included: `sk-lf-abc123-Bearer <token>` comes back as `[REDACTED] [REDACTED]` and `sk-lf-abc123-Authorization: Basic <token>` as `[REDACTED]: Basic [REDACTED]`, and a key found at a place where a character was removed gives the same, since the keyword that ends such a key (`tokenAfterKey`, one test per keyword whatever the key's length) still leads to its token: `x<U+200B>sk-lf-abc-Bearer <token>` comes back as `x[REDACTED] [REDACTED]`, and so after a line break or tab the confirmation drops (`bearer` after an underscore starts no word there either, so `sk-lf-abc_Bearer <token>` keeps its token); (2) the object form, in `sanitize.Payload`: in every JSON object of a payload, at any depth, the value of a member whose key counts is redacted when it is a string `<scheme> <token>` (blanks before the scheme allowed) or a list, each string item of which is checked the same way; the key, the siblings and the rest of the value stay, a value of another type stays, and of two keys that read the same once cleaned the kept value is the redacted one; (3) the quoted text form, inside any string the redactor reads: a quoted name that counts, a colon and a quoted value `<scheme> <token>` (or the first item of a list), the quotes `"` or `'` each written as itself or as a JSON escape (one or more backslashes before it), spaces, tabs and line breaks around the name, around the colon and after the bracket of a list (a pretty-printed map matches; a line break written as an escape does not): the JSON text of a header map, escaped once or more, or a Python dictionary printed as text. The shape is all it checks: a long word or a URL right after `Bearer`, or after a word that reads as a scheme under such a name, is taken for a token. Not redacted: a keyword glued to an ASCII letter or digit that is really there (`xBearer <token>`, `reauthorization: Basic <token>`: the name rule excludes it on purpose and a keyword has no shape that tells it from the end of a word), a shorter token, prose with short words after the keywords, a value with no scheme under such a name (`{"Authorization": "<token>"}`), a header written as a name and value pair (`{"name": "Authorization", "value": "Basic …"}`, a list of two-item lists), a value that is an object, the items after the first of a list in the quoted text form (inside a string that is decoded as JSON text, the object form reads the list and every string item is redacted), a line break written as an escape between a name and its value, and any other header or secret format (cookies, API key headers, query-string tokens). It runs wherever a key is redacted, always before a cut: every payload string and key (before clipping), Langfuse error text (before 500 runes), the operation ID, parameter name and argument name an error echoes (before 64 bytes), the body summary of a confirmation (before 300 runes), the audit line, and a last pass over each result's JSON text. Invisible and control characters are stripped before matching, so a token split by them is found, and are gone from a text that held a secret; tests prove each.
