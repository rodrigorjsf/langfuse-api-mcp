## What was built
When a catalog operation gets an HTML 404 (`langfuse.RouteMissing`), the `operation_unavailable` hint now names the family the catalog puts that operation in. If the family is off in the deployment profile, the hint says so: "the operation is in the v4 read family, which is off on this deployment". If the family is on, the hint says the deployment most likely predates the operation. An operation with no family keeps the previous wording. The version and families on/off summary still follows, and the body is still never echoed. The operation-family type now has one definition, `catalog.Family`. `langfuse.DeploymentProfile.Families` is `[]catalog.Family`, and `langfuse.Family`, its constants and `langfuse.AllFamilies` are deleted.

## Acceptance criteria
- [x] An HTML 404 on a v4-read operation with profile 3.80.0, legacy only, names `v4 read` as the operation's family. Proved by `TestAnHTMLNotFoundHintNamesTheCalledOperationsFamily` (`internal/server/errors_test.go`, MCP tool seam, `observations_getMany`), with two more cases: a legacy op whose family is on, and `prompts_list` with no family. A mutation that drops the family made the test fail.
- [x] The operation-family type has one definition usable by `internal/catalog` without breaking the dependency direction. `catalog.Family` is the only definition, and `catalog` still imports nothing internal. `langfuse` → `catalog` is allowed in `.golangci.yml` depguard (`golangci-lint run`: 0 issues).

## Decisions & deviations
- **Edge `langfuse → catalog`** instead of moving `DeploymentProfile` into catalog. #72's detection (in `langfuse`) must name families, so it needs the type. `catalog` stays a leaf, so there is no cycle. This is recorded as an in-place amendment to ADR-0009, following the amendments already in ADR-0002, 0006 and 0012, and in `project-structure.md` and the `.golangci.yml` header.
- **Deleted `langfuse.Family` outright** rather than aliasing it. One name, no Middle Man re-exports. The cost: #72, built in parallel from the same base, will fail to compile at integration if it uses `langfuse.LegacyFamily` etc. Fix: replace them with `catalog.LegacyFamily` etc.
- `langfuseErrorFields` now takes the `catalog.Operation` instead of the operation ID, so it can read `op.Family`.
- The family is named only when it is in `catalog.AllFamilies()`, as defence in depth. It comes from the embedded catalog, never from Langfuse.
- The archify diagram was not changed: its edges are runtime flows (server→catalog "catalog lookup"), not package imports.

## Code review
Fixed: the duplicated "this route does not exist" prefix (shared const); a leftover `operationID` alias; the reason for the family allow-list check, now stated in the comment; the family-on wording contradicted the families-on summary (spec reviewer), so it now reads "which is not listed as off, so the deployment most likely runs an older Langfuse version".
Dismissed:
- "The amendment needs a new ADR": ADR-0002/0006/0012 set the in-place amendment precedent, and the change does not contradict ADR-0009 (catalog stays a leaf, the direction stays one-way).
- "The archify diagram is not updated": the diagram shows runtime flows, not imports.
- "Several assertions per test": code + hint + version are one logical claim about the hint. The DOCTYPE check is the security "never echo the body" case for the new paths.
- "`DeploymentProfile` and `catalog.Profile` are near-identical": `cmd.catalogProfile` still filters the untrusted version, and #72 rewires this area.
- Scope creep (family-on and no-family branches): these are needed so the hint stays correct for every HTML 404, and they are tested.
