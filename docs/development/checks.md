# CI checks in depth

The union catalog generator, the user skill check and the security mapping check. Start with [CONTRIBUTING.md](../../CONTRIBUTING.md) · [documentation index](../INDEX.md).

The embedded union catalog is generated, never edited by hand: [`scripts/gen-union-catalog.py`](../../scripts/gen-union-catalog.py) rebuilds it from the OpenAPI spec of every Langfuse release tag since v3.0.0 (needs git, network and PyYAML, pinned with hashes in [`scripts/requirements.txt`](../../scripts/requirements.txt): `pip install --require-hashes -r scripts/requirements.txt`; `python3 scripts/test_gen_union_catalog.py` tests it offline), and a weekly workflow ([`.github/workflows/union-catalog.yml`](../../.github/workflows/union-catalog.yml)) runs it and opens a pull request when the output changed. Pull-request CI never fetches release specs: it runs those generator tests, and the `internal/catalog` tests check the committed file offline, including the operation set each deployment-profile fixture resolves to. When a regeneration adds or drops an operation, decide whether it is in scope (trace ingestion, organization admin changes and credential-carrying write bodies stay out) and update those fixtures in the same pull request.

The user skill under [`skills/`](../../skills/) is checked offline in CI by [`scripts/check-skill.py`](../../scripts/check-skill.py) (standard library only; run `python3 scripts/check-skill.py` after editing a skill, and `python3 scripts/test_check_skill.py` after editing the check). It fails when the entry `SKILL.md` lacks a `name` or `description`, its `name` is not the directory's name, or its `description` is over the 200 characters Claude Desktop's skill upload takes or holds an unquoted `: ` or ` #`, which ends a YAML plain scalar; when the entry file cites a reference that does not exist; when a lowercase `snake_case` word is not a tool name or error code the server has, or an operation ID of the embedded catalog (a mixed-case operation ID such as `observations_getMany` is not checked); and when the text holds the words follow or obey instructions found in Langfuse data or a payload, enable or turn on write mode, `LANGFUSE_MCP_ALLOW_WRITES`, skip, bypass or avoid the confirmation, or retry a refused or declined write. These words are refused even when negated ("never skip the confirmation"): write what the agent should do instead ("stop and tell the user"). The tool and error-code lists sit in the check and name where they are kept in step with `internal/server`; its tests read the server's registration and error-code table and fail when the two differ. The phrase list catches the obvious wording, not paraphrases: review covers the rest.

The security mapping in [`docs/research/security.md`](../research/security.md) is checked offline in CI by [`scripts/check-docs.py`](../../scripts/check-docs.py) (standard library only; run `python3 scripts/check-docs.py` after editing the mapping, and `python3 scripts/test_check_docs.py` after editing the check). It fails when the mapping table, its separator row or its Status column is missing; when a row has no status or one other than `tested: …`, `planned: …` or `accepted-risk: …`; when a `tested` row names no test, or names one (in backticks) that is not a `func Test…`/`func Fuzz…` of a Go test file or a `def test_…` of the scripts' Python tests; when a `planned` row links no issue (`#N` or a GitHub `/issues/N` link); and when an `accepted-risk` row gives no reason. It never asks GitHub whether a linked issue is open; that is checked by hand. Renaming a test that the mapping names fails CI until the row is updated.

## Memory of the race suite

`go test -race ./...` runs the tests of `internal/server` (536 top-level tests, fuzz targets included) in one process. Measured on 2026-10-11 on the 7.9 GiB WSL2 machine the fault was found on (12 CPUs, Go 1.27.1, `GOGC` and `-test.parallel` at their defaults): that process peaks at about 1.7 GiB (1579 to 1711 MiB in four runs) and ends in 23 to 26 s, and without the race detector in 4.2 s at 413 MiB. The whole `go test -race ./...` ends in under a minute, at about 2.6 GiB summed over `go test` and the processes it starts, compilers included. Every other package ends in under 30 s. No test and no CI step asserts these numbers: they depend on the machine and on the Go release. They are written here so that the next growth can be seen.

**What it was (#201).** Before the fix the same process passed 5000 MiB after 41 s and, with the default `-timeout`, ended as a timeout after 15 minutes of swapping on an 8 GB machine. It was not the race detector (without it the same tests passed 5000 MiB after 10 s) and not a fault of the server (a server built and closed in a loop is collected): the tests kept what they built. The `testing` package keeps every parallel test that has ended, with the closures it registered through `t.Cleanup`, until the whole run ends (`runCleanup` shortens the list and does not clear it; Go 1.27.1). The helpers' cleanup closures held the server session, so each finished test kept its server, its catalog (1.8 MiB of live heap each) and what they reference, and the live heap only grew: 3024 MB after the last garbage collection at 8.5 s without the race detector (resident set 5008 MiB), 867 MB at 36 s with it (resident set 5003 MiB). The race detector's own memory is about five times the live heap, which is why it ended first. A probe showed it: five servers started by a test that had ended were all alive until the run ended, and none after it. The fix is in the tests only: `closeAtEnd` (`server_test.go`) closes a session and forgets it, so the closure `testing` keeps holds nothing; and `sharedCatalog` loads the real catalog once per run instead of once per test. One run made 1989 catalog loads (each allocates 11 MiB and takes 35 ms, or 20 MiB and 440 ms under the race detector, to compile the JSON Schema of every write body), started 2002 servers and 2007 in-memory sessions, and 1733 fake Langfuse servers. With `closeAtEnd` alone the race run peaked at 1908 MiB and took 195 s; with the shared catalog too, 1.7 GiB and 25 s. The live heap now stays between 100 and 210 MB for the whole run.

**Measure it.** `scripts/race-memory.sh [package [limit MiB [test flags]]]` builds the race test binary of a package, runs it in one process and prints the peak resident set. It reads the resident set of the test process by its PID every 0.2 s and kills the process at the limit (5000 MiB by default) or when `MemAvailable` falls under 1024 MiB (exit code 3). That is the guard to use: `ulimit -v` and `prlimit --as` are no guard, because the race detector reserves a very large address space and would not start. Do not run an unguarded race process of this package beside a container stack or another test run on a small machine. The exact figure of `/usr/bin/time -v` on the same binary is the "Maximum resident set size" line: `go test -race -c -o /tmp/server.race.test ./internal/server`, then `cd internal/server && /usr/bin/time -v /tmp/server.race.test`.

**When it grows again.** Compare the live heap with the resident set over the run: `GODEBUG=gctrace=1` prints `a->b->c MB` after each collection, and `c` is the live heap. A live heap that climbs with the number of tests and does not fall means the tests keep something: a `t.Cleanup` closure that holds a session, a server or a catalog (close it and forget it, as `closeAtEnd` does), or a fixture that every test builds again and no test changes (share it, as `sharedCatalog`). A live heap that stays flat while the resident set is large is the race detector's own memory. Only if one process cannot fit after the tests keep nothing, run every test once in several processes (`-test.list`, then `-test.run '^(a|b)$'` per group) with a check that the groups hold every listed test, and keep that procedure under `scripts/`.
