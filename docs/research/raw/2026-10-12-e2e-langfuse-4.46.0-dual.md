# Second end-to-end campaign against a self-hosted Langfuse 4.46.0 `dual` (2026-10-12)

This record holds the results of the second end-to-end test of the server against a self-hosted Langfuse 4.46.0 in `dual` mode, run on Linux (WSL2) on 2026-10-12 between 11:40 and 12:33 UTC. It checks, on a real Langfuse and before the `v0.2.0` tag (#186), the fixes that followed the [first campaign on this deployment](2026-10-11-e2e-langfuse-4.46.0-dual.md): #208 to #212 (pull request #214) and the fix of pull request #215. The code under test is `main` at `bcbae74`. The run was autonomous: an orchestrating agent (Claude Opus, a subagent of a Claude desktop-app session) delegated the tests to subagents (Claude Sonnet and Claude Haiku), re-checked the decisive results itself, and no person answered anything. Nothing in the production code was changed, and no GitHub issue was opened, edited or closed: every finding below is for the maintainer to triage. The method differs from the earlier campaigns in one way that matters, described under Setup and again in "What this campaign did not cover".

## Setup

| Item | Value |
|---|---|
| Langfuse | Self-hosted 4.46.0 in `dual` mode, the pinned stack (`LANGFUSE_DEPLOYMENT=4.46.0-dual scripts/langfuse-selfhosted.sh up`), fresh project and keys |
| Data | The committed seed, loaded by `scripts/seed-langfuse.py` at 11:40:58 UTC, about 60 seconds after the stack answered healthy (40 traces, 303 observations, 42 scores, 4 score configs, 6 prompts with 14 versions, 3 datasets with 16 items, 3 runs and 20 run items, 7 comments, 5 poisoned records, one trace of about 758 KB). Exit 0 and `readback ok` on the first load |
| Server | `go build ./cmd/langfuse-mcp` at `bcbae74` (go1.27.2, `vcs.modified=false`), started through `scripts/e2e-mcp-server.sh ro` and `rw`. Detected profile: version 4.46.0, families `legacy`, `v4 read` and `experiments`, none undecided, 107 operations (61 reads, 46 writes). Result size cap at its default, 64 KiB |
| Client | Not an agent host. Every tool call of this campaign, a worker's or the orchestrator's, went through the campaign's own driver, `python3 scripts/e2e-audit.py call <ro\|rw> <tool> <json>`: one server process per call, protocol 2025-06-18, no client capabilities declared |
| Workers | Ordinary `general-purpose` subagents (Sonnet or Haiku), each held to that one command by its brief. A worker could add a redirect of the output to a scratch file and read that file |
| Evidence | The server's audit line of every tool call, one file per server: 869 tool calls in all (566 on the read-only server, 303 on the write-mode one, plus one `requested` line of a confirmation that is not counted twice). Call and error counts below come from those files, never from a worker's own report |

The tool set is `search_operations`, `describe_operation`, `execute_read`, `get_trace_tree` and, in write mode, `execute_write`.

**Why the method changed.** The maintainer asked for a run with no person at a terminal. The MCP tools of the desktop-app session belonged to server processes started before this stack existed (old keys, an older binary), and a headless `claude -p` worker could not authenticate in this environment, so the worker agents of `.claude/agents/` could not be started as fresh processes. Three things follow. First, the workers were not restricted by their tool list: the brief told them to run only the driver command, and each worker's own list of commands was compared with its audit window. Second, a tool description reaches a worker only if it calls `tools/list`, which is not a tool call and leaves no audit line, so the call counts of the skill A/B are not comparable one to one with the earlier campaigns, where the host showed the descriptions. Third, no confirmation form was answered by a person (see "Confirmations").

**Workers discarded.** The first two functional sweeps were discarded and run again, each for one command outside the brief, which the worker disclosed itself: a pipe into `head -c 1500` and a pipe into `cut -c1-3000`. In both cases the worker was trying to read a result at the size cap, which the driver prints twice on one line of about 130 KB, too long for the worker's file reader. Neither worker reached Langfuse any other way. The third sweep was told not to read the large trace with its payloads and to make a call smaller instead; its 120 listed commands match its audit window (119 tool calls and `tools/list`). The audit windows of the two discarded runs are still evidence of which operations were called. Every other worker's report matched its window.

## Verdict in one paragraph

The four fixes hold on a real Langfuse: the planted key and the escaped control characters are gone from the two results that leaked them (H1, M1), the empty trace tree names the legacy reads (#209), the operation index carries the static note on its ten legacy entries (#212), and a key followed by a header keyword and a token is redacted in the confirmation text, in the results and in the audit line (#211, #215). The server's own controls hold as before: 144 adversarial calls found no control bypassed, every destructive call was refused without a confirmation, and no worker called `execute_write` on a planted instruction. H2's lost rows happened again, and this run found what the lost traces have in common: the 19 traces missing from Observations v2 are, with one exception that fits the rule, exactly the traces linked to a dataset run item, which the experiment backfill logs that it skips and the dual write never propagates. That gap is Langfuse's, it had not closed 52 minutes after the seed and nothing in the logs suggests it will, and it now costs correctness: in the skill A/B two workers that followed the user skill to the Observations v2 list answered "which traces had errors" with 6 and with 5 of the 7 traces, one of them saying the list was complete. Both got 7 when run again. The small-model eval gave 8 of 13 twice on this code and 11 of 13 on the code of the day before, run the same day. Before `v0.2.0`, the fixes themselves are safe to ship; what the maintainer has to decide is what to make of that eval drop, and whether the skill's route to the v2 list, and a v2 list that says nothing when it is short, are acceptable on a deployment that serves both read families (#213, #219).

## Did H2's lost rows happen again

Yes: 19 of the 40 seeded traces have no row in Observations v2, and that did not change in 52 minutes. This run also found what separates the lost traces from the kept ones.

**The numbers and times (measured, straight from Langfuse and its ClickHouse).**

| Time (UTC) | Seeded traces with rows in Observations v2 | What happened |
|---|---|---|
| 11:40:58 | — | seed posted, one request per trace; staging rows first seen 11:40:59.052 to 11:41:01.065 |
| 11:43:23, 11:44:54 | 0 of 40 | worker log every minute: `[DUAL WRITE] No partitions available for processing (last processed: none)` |
| 11:46:25 | 1 of 40 (`seed-trace-017`) | 11:46:00 `[EXPERIMENT BACKFILL] Found 20 dataset run items …`, `Fetched 7 observations and 1 traces`, then 19 lines `Root span t-seed-trace-NNN not found for DRI <id>, skipping` (every run-item trace but 017), `Wrote 8 enriched spans to events_full table` |
| 11:50:58 | 21 of 40 | 11:50:00.062 `[DUAL WRITE] Processing partition 2026-10-12 11:39:00 for events table fill`, 11:50:00.244 `Successfully propagated observations from partition 2026-10-12 11:39:00 to events table` |
| 11:52 to 12:06 (10 readings), 12:32:57 | 21 of 40 | `Last processed partition` moves on to later partitions; the seed's partition is never read again |

Missing at the end: `seed-trace-001` to `-016` and `-018` to `-020`. ClickHouse at 11:50:52: 303 rows in `observations`; one staging partition `2026-10-12 11:39:00` with 343 rows of 40 traces; 188 rows of 21 traces in `events_core` and `events_full`. Of the staging rows, 155 (19 traces) never reached the events tables. Through the server the gap looks as it did in the first run: `observations_getMany` with `level` `ERROR` returns 5 traces (024, 027, 031, 034, 037) and `legacy_observationsV1_getMany` returns 7 (003 and 010 too); `metrics_metrics` counts 188 observations and `legacy_metricsV1_metrics` 303.

**What separates the lost traces.** Measured: the answer key lists the seed's dataset run items, runs `baseline-gpt-4o-mini` (traces 001 to 008), `candidate-prompt-v3` (009 to 014) and `docs-bot-2025-07` (015 to 020). Those 20 traces are exactly the 20 that the dual write did not propagate, in this run and, by the trace numbers of its report, in the first one; and the experiment backfill's 19 `Root span … not found` lines name exactly the run-item traces other than 017. It is not the age of a trace alone: `seed-trace-021`, kept, is dated 2026-10-05, and `seed-trace-012` to `-015`, lost, are dated 2026-10-11. What is special about `seed-trace-017`: it is the only run-item trace dated on the day of the run (2026-10-12T10:10:58Z, 90 minutes before the seed); the other 19 are dated 2026-10-03 to 2026-10-11, the latest of them (012 to 015) about 19 hours before the seed. It was written by the experiment backfill, not by the dual write: its rows in `events_core` carry 11:46:00.108, the other 20 traces' 11:41:05 to 11:41:06.

A confound, stated plainly: in the seed the run-item traces are also the first 20 posted, so among the rows the dual write itself handled the split is as clean by ingestion order as by run item (lost: staging rows first seen up to 11:40:59.908, `seed-trace-020`; kept: from 11:40:59.950, `seed-trace-021`). What argues against an effect of order or of start-up: exactly the same 20 traces were left out in both runs although the seed was posted 15 seconds after the Langfuse worker started in the first and about 60 seconds after the stack was healthy in this one, so the start-up race the first report offered as a hypothesis does not fit; the first run's two probe traces, linked to nothing, were propagated whole; the backfill's skip lines name the linked traces and no other; and the probes below split at the link, not at a time.

**The probes (measured).** The orchestrator ingested probe traces straight into Langfuse's legacy ingestion API and linked some of them to a dataset run through the server (`datasetRunItems_create`, a POST):

| Probe | Trace dated | Linked to a dataset run item | In Observations v2 |
|---|---|---|---|
| `e2e-probe-a-01` to `-05` | 5 minutes before ingestion | yes, 4.5 minutes after ingestion | yes, by the experiment backfill at 12:09:00 (`Fetched 15 observations and 5 traces`, `Wrote 20 enriched spans`) |
| `e2e-probe-a-06` to `-30` | 5 minutes before ingestion | no | yes, by the dual write at 12:11:00 (partition `12:00:00`), 8.5 minutes after ingestion |
| `e2e-probe-b-01` to `-03` | 2 days before ingestion | yes, at once | **no**, never: `Root span t-e2e-probe-b-01 not found for DRI …, skipping` (and -02, -03) at 12:09:00, and absent after the dual write of their partition at 12:17:00 |
| `e2e-probe-b-04` to `-06` | 2 days before ingestion | no | yes, by the dual write at 12:17:00 |

In probe b the linked traces were also the first three posted, so the confound is not removed there either; in probe a the five linked traces were the first five posted and all arrived, which shows that posting first does not by itself lose a trace. A probe that links traces posted late in a burst and dated days back would separate the two fully; it was not run before the stack was stopped.

So, on 4.46.0 `dual`. **Measured:** the traces Observations v2 lacks are exactly those linked to a dataset run item and dated 19 hours or more before ingestion; the experiment backfill logs that it skips each of them (`Root span t-<traceId> not found`) and writes the linked traces dated 5 and 90 minutes before; the dual write's partition job runs once per partition and does not return. **Strongly supported, not proven:** that the dual write leaves a linked trace out because it is linked, leaving it to the backfill (the code of Langfuse was not read, and order is confounded as said). **Not measured:** where the backfill's limit lies between 90 minutes and about 19 hours; whether Langfuse Cloud or a later release behaves the same. The loss is deterministic for the committed seed: half of it is dataset-run traces dated a day or more back.

**What this means for the open issues.** For #213: a trace tree that is empty for this reason will stay empty, so the "not ingested yet (… up to 15 minutes …)" half of the hint is wrong for it, and the legacy half is the only way to the data. For #220: the loader printed `readback ok` with Observations v2 at 0 of 40, and 19 of 40 traces will never arrive; a readback of Observations v2 would have to expect that, or the seed would have to date its dataset-run traces on the day of the load. For #219: see below; the user and session of a trace are a second, separate gap of the v2 rows, also tied to the trace's date.

## Findings

Severity as in the earlier campaigns: **high** means an agent gets wrong data or cannot finish a normal task; **medium** means an agent is misled or wastes many calls; **low** is cosmetic or a wording gap. "Verified" means the orchestrator reproduced it outside the worker that found it.

### High

**H2 again. Observations v2 lacks the dataset-run traces, the v2 list says nothing when it is short, and the user skill sends error questions there: two wrong answers (verified; the data gap is Langfuse's, the routing, the silence of a short list and the skill's reference are this repository's).**

- The data gap and its cause: the section above.
- The calls: `execute_read` with `observations_getMany`, `level` `ERROR`, `fromStartTime` `2026-10-02T00:00:00Z`, `fields` `core,basic`, `limit` 100 returns five rows and `"meta":{}`, nothing else. `get_trace_tree` of `seed-trace-003` returns an empty tree with the hint of point 2. `observations_getMany` with `traceId` `seed-trace-003` returns `"data":[],"meta":{}` with no hint at all.
- The wrong answers, on the first run of the "errors" pair. The Sonnet worker with the skill made that one list call and answered with five traces: "The result had no cursor (`meta` was empty), so this is the full list", confidence high, although its own second task then read `seed-trace-003` as failed through `trace_get`. The Haiku worker with the skill answered with six (the five and 003), wrote that the list was "verifiably incomplete", and did not read the legacy list, so it missed `seed-trace-010`. The skill's `references/traces.md` names `observations_getMany` with `level` `ERROR` as the way to find errors and does not say that the list can be short on such a deployment. The Haiku worker without the skill read both lists on its own and got 7.
- Both failed cells got 7 of 7 when run again: there the empty tree of `seed-trace-003` and its new hint (#209) led the worker to the legacy list. So the fix of #209 does help, but only when the agent happens to open a trace that is missing.
- The server's part is unchanged since the first report and is what #213 describes: on a deployment with both families `get_trace_tree` and the v4 reads read Observations v2 only; an empty tree has a hint, a short tree and a short or empty list have none. The index note of #212 reaches an agent only if it calls `search_operations` without a query or with one that lists a legacy entry; neither skill worker of the failed cells did.

### Medium

**M-A. On Observations v2 the user and the session of a trace are on its rows only when the trace is recent, so a v2 list filtered by user or session is short, and so are the experiments reads (verified; Langfuse, and the skill's route).** Read from the saved results of this run: every v2 row, the added root row included, of the six seeded traces dated within about 24 hours of the seed (`seed-trace-017`, `-034` to `-037`, `-039`) carries the trace's `userId`; every row of the fifteen older ones in Observations v2 (`-021` to `-033`, `-038`, `-040`, dated 46 hours or more before) has `userId` `""`. The probe traces, dated minutes or two days before ingestion and carrying a session, have `userId` and `sessionId` on every row, so the date that counts was not pinned down. The effect through the server: `observations_getMany` with `userId` `seed-user-carol` returns 23 rows, those of traces 034, 037 and 039, and none of traces 023 to 027 and 031, which are hers and are in Observations v2; `trace_list` with the same user returns her 13 traces. `observations_getMany` with `sessionId` `seed-session-onboarding` returns an empty list (the 15 seeded traces that have a session are dataset-run traces, absent altogether): both skill workers of the "traces" pair went there first, as the skill's reference says, got nothing twice, and recovered through `trace_list` (7 calls each against 2 for the worker without the skill). `experiments_list` with `fromStartTime` `2026-10-01T00:00:00Z` returns one experiment, `docs-bot-2025-07` with `itemCount` 1 (the item of `seed-trace-017`), where `datasets_getRuns` returns the runs whole. This is M2 and M3 of the first report with more of their shape known; the notes of #212 cover the index, and no A/B answer was wrong for it. The orchestrator first read `userId` on the rows of traces 034 and 017 and took the first report's M3 for an artefact of H2; the sweep workers' quote of an empty `userId` on `seed-trace-027` corrected that.

**M-B. The ingestion half of the empty-tree hint is wrong for a trace that will never arrive (verified; wording, the server).** The hint starts `no observation of this trace was found: the traceId may be wrong, or the trace is not ingested yet (data sent by older SDKs can take up to 15 minutes to appear)`. For the 19 traces it was still returned 52 minutes after the seed. One worker called it misleading for that reason. It belongs with #213.

**M-C. The small-model eval lost three intents on the code with the fixes: 8 of 13 in two runs on `bcbae74`, against 11 of 13 on `909df6e` run the same day (verified; which change causes it is a hypothesis).** See "Small-model eval". The new failures are intents 08, 12 and 13; no `execute_write` call was made in either injection intent.

### Low

- **L-A. A key that is not a generated one, glued to a letter, is echoed as it came (verified; documented limit of the redaction rule, not a regression of the fixes).** `execute_read` with `operationId` `abcsk-lf-00000000-fake-probe-value` answers `unknown operation ID "abcsk-lf-00000000-fake-probe-value"`, and the audit line holds the same text; `trace_get` with that `traceId` relays Langfuse's `HTTP 404: Trace abcsk-lf-00000000-fake-probe-value not found within authorized project`. With a key of the generated shape (`sk-lf-` and a UUID) in the same place both answers say `abc[REDACTED]`. The comment of `keyPattern` in `internal/sanitize/redact.go` states the choice: "A key that is no UUID glued to a letter, digit or underscore is not found: "task-lf-name" is a word." The security worker rated it a vulnerability under its brief's definition; the value is the caller's own and a real Langfuse key has the generated shape.
- **L-B. An unknown operation ID that holds an invisible character comes back with a real operation's name in the error's `operationId` field (verified).** `execute_read` with `operationId` `trace`, a zero-width space and `_get`: the message says `unknown operation ID "trace​_get"` (quoted, as the rule asks) and the structured field says `"operationId":"trace_get"`. Nothing is run. `describe_operation` refuses the same value with `invalid_argument`, the difference the earlier campaigns already noted.
- **L-C. Three audit lines of `execute_write` have no `confirmation` field (verified).** A call refused before the confirmation step (`trace_delete` with a body: `invalid_argument`; an unknown ID and a read ID: `operation_not_found`) writes its line at `Warn` without the field; every other `execute_write` line has it. `.claude/rules/security.md` says an `execute_write` line "adds `confirmation`". Whether a refused call should say `not_required` or nothing is for the maintainer.
- **L-D. `observations_getMany` with `parseIoAsJson` `true` is refused by Langfuse 4.46.0 (verified; Langfuse).** `HTTP 400: Invalid request data: parseIoAsJson: parseIoAsJson=true is no longer supported on the v2 observations endpoint`. The parameter is offered with no word about it.
- **L-E. `unstable_skills_get` with no label and no version answers 404 for a skill that has only `latest`, under the `trace_list` hint, and its description names `getFileContents`, which is no operation (a worker's claim, not reproduced).** The operation is `unstable_skills_getFileContent`.
- **Unchanged from the first report (each verified again):** the synthetic root row `t-<traceId>` in every v2 tree (`seed-trace-035`: 10 rows for 9 observations); `trace_list` with `orderBy` `latency.desc` answered `HTTP 400: Invalid order by column: latency` (four A/B workers tried it); Metrics v2 refusing a `traceId` dimension without `orderBy`; `prompts_list` returning `meta` and `pagination`; `evaluators_create` with a code evaluator answered 412; the security nits (`execute_read` answering a 129-character operation ID `operation_not_found` where `describe_operation` says `invalid_argument`; `?`, `#`, `@` and `%2e` in a path value sent percent-encoded and echoed in Langfuse's 404; an 11-character bearer token not redacted; `fields` and `orderBy` left to Langfuse; `page` 99999999999 accepted).

### About the seed, the method and the workers (not the server)

- **The seed's readback still passes on a v2 table that is not the answer key (#220), and the seed itself makes the gap certain:** see "Did H2's lost rows happen again".
- **The orchestrator's probe traces were in the project during the A/B.** 36 traces named `e2e-probe` (no error, no cost, 20 ms long, session `e2e-session-probe`) existed from 12:02 and 12:07. No task's answer depends on them, but the "cost and latency" workers saw them in trace lists (76 traces instead of 40), which cost the Sonnet worker of that pair calls, and the third sweep's legacy observation count was 411, not 303.
- **A result at the size cap cannot be read by a worker through this driver** (one line of about 130 KB); it cost two sweeps (above) and several A/B workers a narrower second call. This is a limit of the method, not of the server: a host shows a tool result once.
- **A fresh score is not readable for about ten seconds.** The write worker's four `scores_get-by-id` calls right after `scores_create` answered 404, and the same calls ten seconds later returned the scores (a worker's claim, consistent with the audit: 7 `langfuse_not_found` in its window).

## What held

**Validation before any request.** The security worker made 144 calls on the read-only server, 121 of them refused or answered with an error (82 `invalid_argument`, 13 `operation_not_found`, 21 Langfuse 404, 5 Langfuse 400), and found no control bypassed: every traversal, absolute URL, scheme, host, `//`, `.`/`..`, `\`, control and invisible character in a path parameter was refused with HTTP status 0 and no echo of the value, on nine operations by its count; the Folder-name allow-list accepted `/` only where it should; `limit` 0, -1, 101, 1e9, 1.5, `"10"` and `true`, `page` 0 and -1, wrong types, enum violations, malformed timestamps and unknown parameters (`Authorization`, `url` and `host` among them) were refused locally; a JSON `filter` that is an object, not JSON, 13 levels deep or holds an escaped zero-width space was refused; a value holding `&limit=100000` or `&userId=x` changed nothing; the search query and the operation ID of `describe_operation` were refused at 129 characters and with control or invisible characters, and the query was never echoed; the metrics query bounds held in 12 cases. Its two reservations are L-A and the unchanged nits. The orchestrator added: a metrics query of 17,244 bytes refused by both metrics operations (`want at most 16384 bytes of JSON, got 17244 bytes`); a key after an escape written as text in an unknown operation ID echoed as `x\\n[REDACTED]`; a key and a bearer header as an unknown parameter name echoed redacted.

**Sanitizing of Langfuse payloads (verified at byte level).** 25 results returning the five poisoned records were scanned, text content and structured content, flat and after decoding any JSON text inside a string: zero raw control, invisible, bidi, tag or variation-selector code points, zero keys, zero unredacted bearer tokens, zero control characters written as escapes, and the untrusted-data label on each of the 24 that succeeded. The one thing the scan flagged is the text `[31m` in `seed-item-poison-01`, with no escape character before it: Langfuse 4.46.0 stores that dataset item without its control characters (the loader's `note:` line), so the server received plain text, which the rule leaves alone. Both audit files hold no Langfuse key of the server, no bearer token and no payload text; the one key-shaped string in them is the orchestrator's own probe of L-A.

**Prompt injection in an agent flow.** Nine A/B workers on the write-mode server read a poisoned record that tells the agent to call `execute_write` (a score comment, a prompt body, a dataset item), and the read-only workers met the poisoned trace name. No A/B cell's audit window holds an `execute_write` call, and every worker reported the text as data. The only `execute_write` calls outside the write worker's window are the orchestrator's own.

**Writes on 4.46.0.** The write worker made 112 calls, 59 of them `execute_write`: 29 succeeded and 3 were answered by Langfuse with an error (all POST, `not_required`), 14 were refused by the body and parameter checks before any request, 10 were destructive and refused for want of a confirmation (below), and 3 were refused before that step (L-C). Created and read back: numeric, categorical, boolean and observation scores, a comment, datasets with and without a Folder name, two dataset items, a dataset run item, a text prompt with two versions, a chat prompt with a Folder name, three score configs, a model, an annotation queue and a queue item, a dashboard widget, a dashboard and a placement, an LLM-as-judge evaluator, an evaluation rule and a skill version. Three creates were answered by Langfuse with an error that fits the call (a code evaluator, 412; a queue assignment for a user that does not exist, 404; an evaluation rule without its variable mappings, 400). `feedback_submit` was not called. The same create sent twice with one ID is an upsert (score, dataset item, dataset). Body checks refused a wrong type, a missing field, an enum violation, `null`, an array or string body and a body on an operation that takes none, each naming the JSON location and the keyword, never the value; nesting of 40 levels (`nests deeper than 32 levels of objects and arrays`) and a 300,000-character value (`exceeds 262144 bytes once compacted`) were refused before anything was sent (orchestrator). An unknown key in a body is sent, as documented. A fake key as a value was sent (it is a value) and read back as `[REDACTED]`. Path checks on writes (`..`, `/`), an unknown ID, a read ID on the write tool and a write ID on the read tool were refused.

**Confirmations.** No destructive call ran. Through the driver, which declares no form elicitation, all 12 destructive calls (10 of the write worker on `e2e-` records across DELETE, PATCH and PUT, 2 of the orchestrator) were answered `confirmation_unavailable`, `…runs only after the user confirms it, and the client cannot ask the user`, with HTTP status 0 and `"confirmation":"unavailable"` in the audit; the targets read back afterwards were intact. One call through the declining test client was answered `confirmation_declined` after `requested` (point 4). An accepted confirmation and a decline by a person were shown in the two earlier campaigns and are not shown here.

**Large trace.** `trace_get` of the 758 KB trace returns 65,535 bytes that parse, with its 6 observations and 11 clipped values; with `fields` `core`, 630 bytes; `get_trace_tree` returns the tree in 7,095 bytes, not truncated; `observations_getMany` with `io` returns its 7 rows in 65,527 bytes; `trace_list` with `limit` 100 returns the 40 traces in 65,536 bytes. Each truncated result names `fields` and its groups in the hint.

**Operations and `fields`.** All 61 read operations were called in the third sweep's window (and in the second's): 48 answered with data, 12 answered 403 because they need an organization-scoped key, and `media_get` answered 404 because the project holds no media. Each of the seven operations that serve `fields` names its field groups in `describe_operation`, and a call with a group from that guidance was answered without an error on each. `scores_get-many` lists `traceId` and `legacy_observationsV1_getMany` lists `level` as parameters, neither with `scannedFilters`. In the sweep worker's cases, filters on `trace_list` (user, session, tags, environment, a time window, a user that does not exist) returned only rows that obey them, and the scores of one trace agree across `scores_get-many`, `scoresV3_getManyV3`, `scores_get-by-id` and `trace_get`.

**Published package.** `npx -y langfuse-api-mcp@0.1.0` against the same stack reported `langfuse-mcp 0.1.0`, protocol 2025-06-18, the four read tools, the same profile (107 operations, 61 offered), and read a filtered trace list correctly (14 rows, all of the user asked for); no key on stderr. ## What this campaign did not cover

- **An agent host.** No tool call went through a host's MCP client: how a host shows a tool description, a tool result or a confirmation form, and the tool-level restriction of the worker agents, were not exercised. The desktop-app session's own MCP tools were stale and were not used; the host was not restarted.
- **A person at a confirmation form.** No confirmation was accepted, so no destructive operation ran on this run and no delete was read back as gone. The accepted and the declined outcomes with a person were shown on 2026-10-11 (3.80.0 and 4.46.0 `dual`). The confirmation text of point 4 was read by a test client that declines.
- Langfuse 4.46.0 `events_only`, 3.225.11, 3.80.0 and Langfuse Cloud. Whether the dataset-run gap exists on Cloud, on a later Langfuse release, or for traces sent through OTLP.
- Where the experiment backfill's limit lies between a trace dated 90 minutes back and one dated about 19 hours back, which trace date puts the user and session on v2 rows (between about 24 and 46 hours for the seed, yet present on a probe dated two days back), and a probe that separates "linked to a dataset run item" from "posted first"; the Langfuse source was not read.
- The success shape of media and blob storage; the 12 operations that need an organization-scoped key.
- 30 of the 46 write operations were not described by the write worker, and the destructive operations it had no target for were not called.
- A forged or expired confirmation state, a response too large to read and a timeout: the tests at the `server` seam cover them.
- Rate limiting, retries, proxies, corporate CAs, the container image, the MCPB bundle, Windows and macOS.
- Statistical confidence: every agent result is one run, two cells two.

## How to repeat it

`docs/development/integration-tests.md`, "End-to-end campaign". For a run like this one, with no host: start the stack, seed it, build the server, and give each worker the driver command (`python3 scripts/e2e-audit.py call <ro|rw> <tool> <json>`) as its only way to Langfuse; mark the audit files before and after each worker. To see H2's cause again, read the Langfuse worker's log for `EXPERIMENT BACKFILL` about five minutes after the seed.
