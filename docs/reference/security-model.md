# Security model

Every security guarantee and how the server enforces it, write mode and its confirmation in full, and how to verify what you run. The essentials are in the [README](../../README.md#security-model) · [documentation index](../INDEX.md).

## Guarantees

Designed against the OWASP Top 10 for LLM Applications (2025 and 2026), the OWASP Top 10 for Agentic Applications (2026), the OWASP MCP Top 10 (2025) and the MCP specification's security guidance. The full mapping is in [docs/research/security.md](../research/security.md): each row carries one status, `tested` (naming the tests that prove it), `planned` (linking the issue that closes it) or `accepted-risk` (with the reason), and CI checks that every named test exists and every `planned` row links an issue.

| Guarantee | How |
|---|---|
| **Read-only unless you opt in** | Langfuse API keys cannot be made read-only, so the server enforces it, for the calls made through the server ([below](../../README.md#keep-the-keys-out-of-the-agents-environment)). Without `LANGFUSE_MCP_ALLOW_WRITES=true` the write tool is not registered at all; `execute_read` runs GET operations only. In [write mode](#write-mode) (a Rule of Two [A,B,C] configuration), `execute_write` runs creates (POST) directly and every DELETE, PUT and PATCH only after the user confirms that exact call through form elicitation; the confirmation is bound to the arguments by a signed, expiring state and fails closed: a client without form elicitation, a declined or cancelled confirmation, or a forged, expired or rebound state refuses the call before anything is sent. The tool set is fixed at startup: no client capability sent in the handshake, no `server/discover` probe (however early it arrives, before, between or after the `initialize` messages), and no second `initialize` changes it (tested). |
| **No data kept** | Stateless. No cache or database, no files written. |
| **Your keys stay with the server** | Read only from the server's environment; a config file holding a key stops startup, and the warning for an unknown config-file key names the key (escaped and shortened) but never its value, so a key filed under a misspelled name is not logged. Never accepted from the agent, never logged, never included in results: if Langfuse or the agent echoes a key or the `Authorization` header, it is replaced by `[REDACTED]`. Inside the server the keys, from the moment they are read, travel only in types that print as `[REDACTED]` through every format verb, JSON and log call. Proxy credentials (`user:password@` in `HTTPS_PROXY`) are used only for Basic proxy authentication: the startup log shows the proxy as `scheme://host:port`, and an invalid proxy value stops startup without being echoed. |
| **A credential copied into your data is redacted** | A header or bearer token that a trace, a prompt or a Langfuse error text holds is replaced by `[REDACTED]` in every tool result, tool error, hint and log line, like a Langfuse key. The scheme word stays: `Authorization: Bearer seed-fake-bearer-token-00000000` comes back as `Authorization: Bearer [REDACTED]`, and `{"headers": {"Authorization": "Basic dXNlcjpwYXNzd29yZDEyMzQ1Njc4"}}` as `{"headers": {"Authorization": "Basic [REDACTED]"}}`. A scheme is a letter followed by letters, digits and `_ . + -`. A token is a run of at least 16 printable ASCII characters other than space, the quotes `"`, `'` and `` ` ``, and the backslash, so white space, a closing quote or a JSON escape ends it. A credential that holds one of those characters, or a non-ASCII one, is redacted only up to it, and only if the part before it has 16 characters. One rule decides which names count, for every form: a name counts when, with invisible and control characters stripped, surrounding blanks dropped and case ignored, it is `authorization` or ends in `authorization` after a character that is not an ASCII letter or digit (`Authorization`, `AUTHORIZATION`, `Proxy-Authorization`, `X-Upstream-Authorization`, `http.request.header.authorization`, `HTTP_AUTHORIZATION`). A name that only contains the word (`authorizationMode`, `authorization_url`, `reauthorization`) does not, and nothing in a payload or a tool argument changes the names, the schemes or the minimum length. Exactly these forms are redacted: (1) `<name>: <scheme> <token>`, with blanks (spaces or tabs) around the colon and at least one before the token, and `Bearer <token>` (the word in any case at the start of a word; a hyphen starts one); (2) in every JSON object of a result, at any depth, the value of a member whose key counts, when it is a string `<scheme> <token>` (blanks before the scheme allowed) or a list, in which case each string item is checked the same way (`{"Authorization": ["Basic …"]}`); the key, the other members and the rest of the value stay; (3) inside any text the server reads (JSON text in a trace input, a Langfuse error message, a name the server echoes, the summary of a confirmation), a quoted name that counts, a colon and a quoted value `<scheme> <token>`, or the first item of a list, with the quotes `"` or `'` written as themselves or as a JSON escape (`{\"Authorization\": \"Basic …\"}`), or in a Python dictionary printed as text; spaces, tabs and line breaks may sit around the name, around the colon and after the bracket of a list, so a pretty-printed map matches. The shape is all the server checks, so a long word or a URL right after `Bearer`, or right after a word that reads as a scheme under such a name, is taken for a token (`Use Bearer authentication-required here` comes back as `Use Bearer [REDACTED] here`, and `{"authorization": "see https://docs.example.com/auth"}` as `{"authorization": "see [REDACTED]"}`). Left alone: a token of 15 characters or fewer, prose with short words after the keywords ("the Bearer scheme", "Authorization: required"), a value with no scheme under such a name (`{"Authorization": "<token>"}`: a single word is too often data, as in `"authorization_code"`), a header written as a name and a value in two members (`{"name": "Authorization", "value": "Basic …"}`, a list of two-item lists), a value that is an object, the items after the first of a list inside text, a line break written as an escape between a name and its value, a token on the line after the word, and any other header or secret format (cookies, API key headers, query-string tokens). An invisible or control character inside a credential or a name does not hide it: the text is matched without them. The redaction runs before the result is clipped, before an error message or an echoed name is cut, and before the confirmation of a destructive write cuts the body summary, so a token a cut would have left short is replaced whole. It changes only what is shown or logged: the request sent to Langfuse, and the call you confirm, are the ones the agent wrote. |
| **No arbitrary requests** | The agent picks operations from a fixed catalog. Every parameter value is checked against the operation's type, allowed values and the numeric and length bounds its spec gives (the ones `describe_operation` reports; on a parameter with no declared type, by whether the value is a number or a string), before any request; a refusal names the parameter and the bound, never the value. The text of a value is checked too: a control or invisible character (zero-width, bidi, tag and variation-selector characters among them) in a path parameter is refused, never removed, so the server never looks up an ID you did not send; in a query parameter value, a list item included, and in a metrics query it is refused as well (tab, line feed and carriage return too; only the blanks between the tokens of a JSON filter may be them); `page` below 1 is refused; and where the spec says a parameter is a `date-time`, only an RFC 3339 timestamp passes. Each refusal names the parameter and the rule and never repeats the value. `orderBy` is left to Langfuse. The server decodes the metrics query and every JSON `filter` (`trace_list`, `legacy_observationsV1_getMany`, `observations_getMany`, `scores_get-many`, `experiments_list`, `experiments_listItems` and `prompts_list`) before it sends them: a filter must be a string holding the JSON text of one list, at most 16384 bytes and 10 levels deep, and no string or key of it may hold a control or invisible character, written as itself or as a JSON escape. The server sends the list it checked, written again as compact JSON, so a duplicated key keeps only its last value and no escape of a hidden character reaches Langfuse; the columns, operators and types of a condition stay Langfuse's to check. The `filter` of `scim_listUsers` is a SCIM expression, checked like any query parameter value. It cannot pass URLs or hosts; path parameters that could change the path (`/`, `\`, `.`/`..` segments, URLs) are refused. Only the prompt and dataset name parameters on a fixed allow-list (four reads, four writes) accept `/` for a Folder name, sent encoded as `%2F` so it stays one path segment; `.`/`..` segments, empty segments and a leading or trailing `/` are still refused there. An operation ID the Langfuse releases know but your deployment does not offer is answered `operation_unavailable` from the bundled catalog alone, with a fixed hint (replacements, version, families), never with text from your call; a write operation ID while writes are off is `operation_not_found`. A redirect to another scheme, host or port is refused before it is sent, so your keys never leave the configured host. |
| **A parameter your Langfuse version ignores is refused** | An operation offers only the parameters your deployment's Langfuse version serves. A call carrying another parameter of the operation is refused before any request, with a message naming the parameter, the operation, your version and the release that serves it (never the value), so the agent never receives unfiltered data as if it were filtered. With no detected version, the newest release's parameters are served and the startup log says so. |
| **A filter your Langfuse version lacks is applied by the server, within bounds** | For `traceId` on `scores_get-many` and `level` on `legacy_observationsV1_getMany`, the only two pairs of a fixed list, the server reads the list without the filter and keeps the matching rows. The filter's value gets every check of a value that is sent. The scan reads at most 10 pages of 100 rows whatever the call asks (no argument raises it, and `page` is refused), inside the request limits shared by every call, and counts its requests in the audit line. Rows are compared after cleaning and redaction and come back only as data in the untrusted-data envelope; the summary says whether the scan was complete, how many rows it read of how many exist, in static text and numbers. A failed page ends the scan with no rows. An operation description shows the filter apart from the served parameters, with a fixed note, only on a deployment that scans it; the hint of a refused call names it with one fixed clause. Neither depends on an argument, a payload or a client, and neither holds a value or text of the call. |
| **Every change is tested against injection** | Each tool, operation or parameter ships with tests for prompt injection in Langfuse payloads and for dangerous parameters (unknown names, URLs, traversal, control characters, out-of-range values); see the [roadmap security gate](../../ROADMAP.md#security-gate-every-milestone). The user skill's text is checked in CI too: it may not tell the agent to follow instructions found in Langfuse data, enable write mode or work around a confirmation, and every tool and error code it names must exist in the server. |
| **No local system access** | No shell commands, no file access beyond reading the CA files you configured and the optional [config file](configuration.md#config-file-non-secret-settings). |
| **Verified TLS only** | OS store + your CAs, TLS 1.2+, no skip-verify option. |
| **Untrusted data is labelled** | Trace and prompt content returned to the agent is marked as untrusted data and cleaned of hidden Unicode (zero-width, bidi, tag and variation-selector characters) and control characters, a terminal escape sequence (a colour, a cursor movement, an OSC 8 hyperlink with its URL) removed whole, not with its escape character alone, by a scan that reads at most 256 characters from the escape character, so a payload cannot make the server drop more text than that and text such as `[31m` with no escape character before it is never changed; the removal runs before redaction, so a key hidden behind or split by a sequence is still redacted, and Langfuse error text is cleaned the same way. The operation descriptions `search_operations` and `describe_operation` show come from the bundled spec, cleaned of the same characters, with Markdown links and bold markers reduced to their text and each line cut at 200 characters, and both tools say the descriptions are third-party text to read as data, not instructions; the request body schemas the bundled catalog keeps for write operations are cleaned of the same characters, in every string, when the server starts; a `query` longer than 128 characters or holding a control or invisible character is refused, and the query is never repeated in a result or an error; `describe_operation` also lists, apart from its parameters, the filters the server applies itself on this deployment, only for the two filters of the filter scan and only where the version detected at startup does not serve them, never because of an argument, a payload or a client, each with the facts of a parameter and one fixed note; the trace reads hint of a search, given only to a search about traces, is fixed text, and so are the guidance `describe_operation` gives on the metrics queries, the `prompts_list` `tag` and `filter`, the `prompts_get` `label` and `version` and the `fields` of the seven operations that take it (#178, #194: the field groups, from one compiled list that the hints that recommend fewer fields name too, `trace_list`, `trace_get`, `observations_getMany`, `scores_get-many`, `scoresV3_getManyV3`, `experiments_list` and `experiments_listItems`, each only on a deployment that serves `fields` on it), the hint of a refused metrics query and the hint of a `prompts_get` 404 that names the implicit `production` label, which never repeat the query, the prompt name, the value of `fields` or any other caller input or Langfuse data. An operation ID that `execute_read` does not know comes back in its error shortened and cleaned of the same characters. A `get_trace_tree` `traceId` longer than 128 characters or holding a control or invisible character, an `include` other than `io`/`metadata` and any unknown argument are refused before Langfuse is called, without repeating the value; the `traceId` is sent only as a query parameter. On a deployment that answers neither the v4 read APIs nor the legacy APIs the tool is still listed, and a call that passes those checks is answered `operation_unavailable` with fixed text that names the deployment's version and the operation that reads one trace there, never the `traceId`, and sends no request; the tool set is the same on every deployment and for every client. On a deployment that answers only the legacy APIs the tool builds the trace tree from the legacy observations list: at most 10 pages of 100 observations whatever the call asks (no argument names a page, a limit or a field), through the same rate limit and concurrency cap as every request, each page cleaned and redacted before its rows are read, and input, output and metadata removed from every row by key name at the top level unless `include` asks for them, so a hidden character or an escape written into a key cannot keep them; then each top-level key whose value is JSON `null` is left out (the legacy list sends most of its 39 keys as `null`), except `id`, `parentObservationId` and `startTime`, which the tree is built from. Only the type `null` counts: a key that holds the text `"null"`, an empty string or `0` stays, nothing inside a value changes, the rule runs on the cleaned row (so a `null` key with a hidden character in its name goes and cannot shadow a kept key), no argument, payload or client turns it on or off, and it adds no text to a result, hint or `meta`; its rows come back only as data in the untrusted-data envelope, a page that fails ends the call with its tool error and no partial tree, and its hints are static text plus page numbers, never the `traceId` or payload text. The continuation cursor of a long trace is Langfuse's data: it is returned only inside the untrusted-data envelope, never in a hint or the log, and `execute_read` sends it back unchanged, never decoded. The text a proxy sends when it rejects the tunnel is dropped: the agent and the log only see `network_error`. |
| **Bounded** | Timeouts, a default and maximum `limit` on list operations and `config.row_limit` on metrics queries, a size and depth bound on the metrics query JSON, a 256 KiB and 32-level bound on a write body, checked before its JSON Schema (refused before it is sent, never echoed), no automatic retry of a write, at most 5 MiB read from Langfuse and, by default, 64 KiB returned per result (a result over it has its largest string values clipped, each keeping its start and ending in a fixed marker, and only if that is not enough rows left out at a row boundary, always saying `truncated`; clipping runs after the payload is cleaned and redacted, so it cannot bring back a hidden character or a secret, and the marker and the hint are fixed text that holds no payload text; the operator sets it with `LANGFUSE_MCP_MAX_RESULT_BYTES`, 16384 to 1048576, in the environment or the config file, never a tool argument; an invalid value stops startup naming the variable and its source, never the value; the discovery tools' results are bounded by the same cap but never cut at a byte: a body schema that does not fit loses only its `description` and `title` annotations (and, if that is not enough, is left out whole), an operation index that does not fit keeps its leading entries, both saying `truncated` with a fixed hint that holds neither the query nor any catalog text, and `execute_write` always checks a body against the full schema; a host may have its own, lower limit for showing a result, see [Result size cap](configuration.md#result-size-cap)). Langfuse's `Retry-After` is honored. Every Langfuse request, retries included, waits on one shared rate limit and a cap on requests in flight, set only by the operator (`LANGFUSE_MCP_RATE_LIMIT`, `LANGFUSE_MCP_MAX_CONCURRENCY`, see [Request limits](configuration.md#request-limits)); unset, the rate limit defaults to 30 per minute on a Langfuse Cloud host and 1000 on any other host. |
| **HTTP mode is local-only** (**Planned**) | The HTTP transport does not exist yet; when it ships, it binds to `127.0.0.1` with a random bearer token and `Origin`/`Host` checks. Today the server speaks stdio only. |
| **Auditable** | One log line per tool call on stderr (metadata only, no payloads, and no request URL or redirect target when a request fails); an `execute_write` call is logged at `WARN` with its `confirmation` outcome, never its body. The reported server version is the one injected at build time or a release tag from the build info, never another build-metadata string. Open source (Apache-2.0). |

Recommendations: create a dedicated Langfuse key for the agent, set an expiry date on it, and keep writes off unless you need them.

Found a vulnerability? Report it privately, never in a public issue: see [SECURITY.md](../../SECURITY.md).

## Write mode

Off by default, and then `execute_write` does not exist: the agent cannot even try a write through this server (a tool that holds the keys itself is outside that gate: [Keep the keys out of the agent's environment](../../README.md#keep-the-keys-out-of-the-agents-environment)). With `LANGFUSE_MCP_ALLOW_WRITES=true` the server registers `execute_write`, and `search_operations` and `describe_operation` list write operations too, each naming the tool that runs it; the operation index also gives each write operation's HTTP method and whether it is destructive, so the agent knows which calls ask you to confirm without describing each one. While writes are off, no tool shows that a write operation exists: `execute_read` and `describe_operation` answer a write operation ID with the `operation_not_found` they give an ID that is in no release, in the same words, without an HTTP method. The tool set is fixed at startup, the same for every client. Enabling writes gives one agent untrusted input (Langfuse payloads), your project's data and the power to change it at once: the Rule of Two [A,B,C] configuration of LLM01:2026 ([docs/research/security.md](../research/security.md)), where a prompt injected into a trace could steer a write. The server's guards (below) narrow that risk; the confirmation of destructive operations is the per-call human check the server enforces, and your MCP client's own permission prompt is the one for creates.

- Creates (POST), such as `scores_create`, `comments_create` or `datasetItems_create`, run without a server-side confirmation. A known limit: `prompts_create` with the `production` label also changes the prompt Langfuse serves, and it is still a create, confirmed only by your client's permission prompt.
- Every destructive operation (DELETE, PUT, PATCH) runs only after you confirm that exact call. Its arguments are checked first; then the server asks you through your client's form elicitation, with a multi round-trip request (MCP 2026-07-28; for a client on an older protocol the SDK asks directly, with the same checks). Over stdio every client is on an older protocol, because stdio does not offer 2026-07-28: a `server/discover` probe is answered with the older protocols and negotiates nothing, even when it is already waiting in stdin when the server starts reading, and the `initialize` after it succeeds (see **Protocol.** under [Claude Code](configuration.md#claude-code--proven)). The question names the operation ID, the HTTP method, the path and query parameters and a summary of the body, cut at 300 characters (it then says so and gives the body size in bytes); for `trace_deleteMultiple` it gives the number of trace IDs. Every value is stripped of control, invisible and bidi characters and shown quoted, as text: markup is never rendered or escaped by the server, so `<b>` reads as `<b>`. The MCP elicitation message is plain text; a client that rendered Markdown or HTML in it would be the one to render it, and the quotes still mark the value as argument data.
- The confirmation is bound to the call: the server's answer carries a state signed with a key drawn at startup (HMAC-SHA256 over the operation ID and the checked arguments, re-encoded; never logged or stored) that expires after 5 minutes. It fails closed, and in each case nothing reaches Langfuse: a client that offers no form elicitation (none, or URL mode only; read per request) gets `confirmation_unavailable`; declining or cancelling gets `confirmation_declined`; an accept sent before the server asked, re-sent with other arguments, or with a forged, corrupted, expired or another process's state gets `confirmation_invalid`. There is no setting that skips it. Replaying the identical confirmed call within the 5 minutes is not prevented; every confirmed method is idempotent.
- A host without form elicitation cannot run destructive operations at all; make those changes in the Langfuse UI. Claude Code supports form elicitation from v2.1.76.
- `media_getUploadUrl` and `media_patch` (a media upload needs a byte upload this server never makes) and `llmConnections_upsert` and `blobStorageIntegrations_upsertBlobStorageIntegration` (their bodies carry a third-party credential) are excluded.
- Every body is checked against the operation's JSON Schema before it is sent (see `execute_write` in [How it works](tools.md#how-it-works)); `describe_operation` returns that schema, whether the operation is destructive and, for `comments_create` (where its `projectId` comes from) and `scores_create` (that a score needs one target), a fixed `body.guidance` that is compiled into the binary and holds no caller input and no Langfuse data. Unknown keys are refused only where the schema forbids them. No in-scope schema does today, so a misspelled optional key is not caught by the server: it is sent with the rest of the body, and Langfuse may ignore it without an error (a [known limit](tools.md#known-limits); a catalog test fails if a regenerated catalog forbids unknown keys anywhere). The server cannot tell a misspelled key from a property that a Langfuse release accepts, and refusing every unknown key would break valid calls.
- A write is never retried automatically: on a 5xx, a 429 or a network error the agent gets the tool error with a hint that the write may or may not have been applied.
- Each `execute_write` call logs its audit line at `WARN`, with `confirmation` and never the body: `not_required` for a create; for a destructive call `requested` (the round that asked), `accepted`, `declined`, `unavailable` (the client cannot ask) or `invalid` (confirmation data refused); absent when the call was refused before its confirmation started.

## Verify what you run

The release workflow signs and publishes **only on a `v*` release tag**, never on a pull request, a push to `main` or the weekly run. A cosign keyless signature writes a permanent public entry (the Rekor transparency log) naming this repository and its workflow. Every command below passed against `v0.1.0` ([record](../research/raw/2026-09-30-v0.1.0-release-proofs.md)).

Every release carries: `checksums.txt` (SHA-256 of every archive and of its SBOM); one SPDX JSON SBOM per archive and one for the image; a cosign keyless signature, as a Sigstore bundle `<file>.sigstore.json`, and GitHub build provenance for every archive, `checksums.txt`, the `.mcpb` and the skill ZIP; the multi-arch image signed by digest (each platform image too) and attested by digest. The archive SBOMs are covered through `checksums.txt`, which lists them and is itself signed. The `.mcpb` and the skill ZIP are not in `checksums.txt` (GoReleaser writes that file before they are packed): check them by their signatures (step 2). The image SBOM (`langfuse-mcp_<version>_image.sbom.json`) is covered by no signature yet: neither `checksums.txt` nor a bundle or attestation lists it. A signature is valid only when its certificate names this repository's release workflow at the release tag, issued to GitHub Actions. Step 4 needs a GitHub CLI with the `gh attestation` command (the Ubuntu package's 2.45.0 lacks it; 2.101.0 has it). With the release files downloaded into the current directory (see [Release archive](installation.md#release-archive)):

```bash
version=<version>   # without the leading v, for example 0.1.0
archive="langfuse-mcp_${version}_linux_amd64.tar.gz"   # the archive you downloaded

# 1. The archive is the one in checksums.txt (Windows: compare Get-FileHash, see Release archive).
awk -v f="$archive" '$2 == f' checksums.txt | sha256sum -c -   # macOS: … | shasum -a 256 -c -

# 2. The archive, checksums.txt, the .mcpb or the skill ZIP was signed by this repository's release workflow.
identity="https://github.com/rodrigorjsf/langfuse-api-mcp/.github/workflows/release.yml@refs/tags/v$version"
for f in "$archive" checksums.txt "langfuse-mcp_${version}.mcpb" "langfuse-api-mcp-skill_${version}.zip"; do
  cosign verify-blob --bundle "$f.sigstore.json" \
    --certificate-identity "$identity" \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com "$f"
done

# 3. The image was signed by the same workflow.
cosign verify ghcr.io/rodrigorjsf/langfuse-api-mcp:$version \
  --certificate-identity "$identity" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

# 4. GitHub build provenance: built by this repository's workflow from the tagged commit.
gh attestation verify "$archive" -R rodrigorjsf/langfuse-api-mcp
gh attestation verify oci://ghcr.io/rodrigorjsf/langfuse-api-mcp:$version -R rodrigorjsf/langfuse-api-mcp
```

The npm packages are published with npm provenance: `npm audit signatures` in a project that installed `langfuse-api-mcp` checks them (for `v0.1.0` it reports verified registry signatures and attestations for both installed packages).

The [npx](installation.md#npx) channel adds the npm registry and Node.js as dependencies of that channel only; its packages depend on nothing but their own platform packages and run no install script. The one Python dependency of the maintainer tooling (PyYAML, used by the union catalog generator in CI only) is pinned with hashes in [`scripts/requirements.txt`](../../scripts/requirements.txt), installed with `--require-hashes` and kept current by Dependabot. The MCPB CLI that validates and packs the Claude Desktop bundle is pinned with its whole dependency tree and integrity hashes in [`packaging/mcpb/package-lock.json`](../../packaging/mcpb/package-lock.json), installed with `npm ci --ignore-scripts` and kept current by Dependabot. `mcp-publisher`, which publishes the [MCP Registry](https://registry.modelcontextprotocol.io) entry on a release tag only (`publish-registry`), is pinned to one version and its archive checked against a pinned SHA-256 before it runs; the entry it publishes is [`packaging/server.json`](../../packaging/server.json), whose texts are written in this repository and never built from Langfuse data.
