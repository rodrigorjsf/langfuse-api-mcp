## What was built
- A Langfuse key as Langfuse generates it (`pk-lf-`/`sk-lf-` and a UUID) is redacted wherever it stands, glued to a word too (`xsk-lf-<uuid>` gives `x[REDACTED]`). Any other key keeps the word-boundary rule: `task-lf-name`, `xsk-lf-abc123`, `task-lf-normalize-all-inputs` come back as they were.
- `Bearer <token>` and the plain `Authorization: <scheme> <token>` form (any name the name rule accepts) are redacted directly after a JSON escape written as text (the escapes of #208, one rule `wordEndedEscape`) and directly after a place where the cleaning removed a character (#210's mechanism, `redactAfterPlaces`, now serving the key and the header keywords).
- The confirmation body summary uses `sanitize.LineValue(v, r)`, which records where `Line` dropped a tab, line feed or carriage return and redacts there: a key or token after a dropped break is redacted, one a dropped break splits is found whole, the 300-rune cut still follows the redaction.
- The audit line redacts the operation ID before it drops the hidden characters (option 5 of the ticket's second comment).
- Found by review and fixed: the token of an earlier credential runs to the next blank and swallowed a keyword that a removed character glued to it, so two credentials on two dropped-break lines left the second one in the clear. A keyword within 64 bytes after a place, in the same run of token characters, is now a start (`Proxy-Authorization` and dotted names included).

## Decisions & deviations
- Maintainer choices were settled by the triage comment on #211 (design decisions 1 to 6): generated-key shape needs no boundary; a non-UUID key glued to a word character stays unredacted and documented; header keywords after an escape or a removed place are starts; a keyword glued to a real letter or digit stays unredacted (name rule).
- Existing expectations that changed: `sanitize.LineValue` now takes a `Redactor` (`headermap_test.go` call updated); the tests that pinned a key after a dropped line break as shown and a key after a hidden character in the audit line as shown were removed (their cases live in `gluedcredential_test.go`, reversed); the pinned expectation `Bearer abc…<ZWSP>Bearer <token>` -> second token in clear was reversed by the review fix (now `Bearer [REDACTED] [REDACTED]`).
- The hostile "key prefixes" string uses `8*n` instead of `2*n`: the larger key pattern lowers the size at which Go's regexp switches from its backtracker to the automaton, and both inputs of a time-proportion pair must be on the same engine.
- Review fix, design: after a place, `tokenAt` looks for a keyword within `maxKeywordReach` (64) bytes in the same run of token characters (`isValueChar`), with the boundary rules of `headerPattern` (`authorization` after a non-alphanumeric, `bearer` at a word start, the place itself a start). The `insideAMatch` guard is dropped for headers (kept for keys, where whole-key matches make it harmless). A name that puts the word farther than 64 bytes away stays the pattern's business and is documented.
- The audit line reorder (`sanitize.Text(r.Redact(...))`) is the ticket's second comment, not scope creep.
