## What was built
- On a deployment where the legacy family and the family of a preferred operation are both on (Langfuse 4.46.0 `dual`, Cloud until 2026-11-16), `search_operations` gives ten legacy read entries a `note`: the preferred operation (named by its catalog ID) reads another store and can return less than this operation, or nothing, for data written through the legacy APIs, so an empty or short result is worth checking with this operation. It states a possibility.
- The ten: `trace_get`, `trace_list`, `sessions_get`, `sessions_list`, `legacy_observationsV1_get`, `legacy_observationsV1_getMany` (`observations_getMany`), `legacy_metricsV1_metrics` (`metrics_metrics`), `datasets_getRuns`, `datasets_getRun` (`experiments_list`), `datasetRunItems_list` (`experiments_listItems`). With the experiments family off, only the seven that prefer a v4 read operation.
- The note is an optional string key `note` of the entry (declared in the output schema as static text written by this server) and, in the text, ` | note from this server: <note>` after the description and, in write mode, after the `(execute_read)` parenthesis. `description`, the `legacy: prefer … when it is available` mention and the order of the index are unchanged.
- The trace reads hint on a profile with both the v4 read and the legacy family keeps today's text and adds one sentence: this deployment also serves the legacy reads, which may hold data sent through the legacy ingestion API that the reads above lack, then `execute_read` with `trace_get`, `trace_list`, `legacy_observationsV1_getMany`, `legacy_metricsV1_metrics`, each only if the catalog offers it.
- 3.80.0, 3.225.11, 4.46.0 `events_only` and the no-families profile: text, structured content and hint byte for byte as before.

## Decisions & deviations
- Design as the triage comment chose: a family rule decided in `Catalog.Resolve` (`Operation.PreferredOfOtherFamily`, field `otherFamilyPreferred`), a note beside the line, no ADR change. Conditions: legacy read, line names a preferred operation, it is offered as a read operation, its family is not empty or legacy, both families in `Profile.Families`, and the families were applied (`byFamily`, i.e. not below the supported floor).
- `catalog.Load()` and `UnknownProfile()` resolve with every family on, so an undetected version with all families on gets the ten notes (the ticket lists "no detected families" as unchanged, which is the empty `Profile{}`, and that one is). Consequence: existing tests on the default catalog changed — `TestSearchOperationsListsALegacyReadByWhatItDoesAndItsReplacement` (line may be followed by the note), `TestAReadLineOfTheOperationIndexGainsNothing` (note segment left out), and the read index budget `TestSearchOperationsWithoutQueryListsTheReadIndexWithinItsBudget`: 7,222 bytes before, 9,910 with the notes (about 269 bytes a line, more than the ticket's ~150 estimate; the wording is the ticket's), cap raised 8 KiB to 11 KiB (margin 1,354 bytes). The figure was updated where the test comment says to: ADR-0002 (a measured figure, not a decision), and story 12 of the closed spec #68 (patched with `gh api -X PATCH`; only that sentence differs, checked by diff, state still closed).
- Text layout: the note comes after the description and after the write-mode `(execute_read)` parenthesis, behind the label ` | note from this server: `. Chosen so the label keeps it apart from the third-party description and so a read line still ends its description part with the tool as before.
- The `search_operations` tool description was not changed (the ticket says it "may" gain a sentence): the output schema and the label on the line carry the fact, and the description stays identical on every deployment.
- The unchanged-index checks are digests, not text goldens: a golden file `testdata/search-operations-digests.json` with an explicit `-update` flag (first use of that pattern in the repo; documented in `docs/development/checks.md` for the weekly catalog regeneration). Review of the first version (digests inline in the test) called that a breach of `testing.md`.
- `CONTEXT.md` Operation index entry got a clause (the ticket said "no term changes"; no term was added or redefined, the entry only lists what an entry may hold).
