# Security: requests to Langfuse

Part of the non-negotiable security rules (`security.md`), moved here verbatim so it loads only with the code it governs. Keep this text and the invariant line in `security.md` in step.

**Requests to Langfuse**
- Model input selects an operation ID + params; every value is checked against the operation schema (type, enum, and the spec-given `minimum`/`maximum` and `minLength`/`maxLength` in runes, after the list `limit` check so `limit` keeps its own error and hint; a schema without a type bounds a JSON number by value and a string by length, #83; the refusal names the bound, never the value, #80) and unknown params are rejected; reject absolute URLs, schemes, hosts, `//`, `.`/`..` segments, `/` and `\` in path params; percent-encode path params. `/` is accepted only for a Folder name on the static, fail-closed allow-list of `(operationId, parameter)` in `internal/catalog` (`prompts_get`/`promptName`, `datasets_get`/`datasetName`, `datasets_getRuns`/`datasetName`, `datasets_getRun`/`datasetName`; writes, #113: `prompts_delete`/`promptName`, `promptVersion_update`/`name` and, before 3.18.0, `promptVersion_update`/`promptName`, `datasets_deleteRun`/`datasetName`), sent as `%2F`, with no empty, `.` or `..` segment; a refusal message never contains the value (#33). The text of a value is checked before any request (#179): a control or invisible character (the set `sanitize.Text` strips from a payload, plus tab, line feed and carriage return; `TestAPathParameterRefusesExactlyTheCharactersTheSanitizerStrips` pins the two) in a path parameter is refused, never removed, so no ID the caller did not send is looked up (a Folder name on the allow-list included); in a query parameter value, a list item included, it is refused too (tab, line feed and carriage return are control characters there as well; only the blanks between the tokens of a JSON filter may be them), and so is one in a metrics `query` once decoded, written as itself or as a JSON escape; a JSON filter (#195) is read as the metrics `query` is: the closed list `jsonFilters` in `internal/catalog` names the `filter` parameters that are a JSON text (`trace_list`, `legacy_observationsV1_getMany`, `observations_getMany`, `scores_get-many`, `experiments_list`, `experiments_listItems` and `prompts_list`), the `filter` of `scim_listUsers` is a SCIM expression and an ordinary query parameter value (`plainFilters`), and a test fails, naming the operation, when an operation of the union catalog has a `filter` on neither list; a JSON filter must be a string holding the JSON text of one list with nothing after it, at most 16384 bytes and 10 levels deep (the bounds of the metrics `query`, checked before the text is decoded), with no control or invisible character, first as raw text (tab, line feed and carriage return allowed between tokens) and then in every decoded string and object key, so a JSON escape of one is refused like the character itself; the server sends the decoded list written again as compact JSON (conditions and list items in order, numbers as written, object keys sorted, a duplicated key once with its last value, no escape of a hidden character or of half a surrogate pair), so Langfuse reads the text that was checked; anything else is `invalid_argument` naming `filter` and the rule or the bound, never the value, with the static hint `catalog.JSONFilterHint` (not the metrics query hint), the grammar of a condition (columns, operators, types, keys) stays Langfuse's, a `filter` the version does not serve is refused first (#173) and `describe_operation` gains no guidance for it; `page` below 1 is refused, the refusal naming its minimum; a parameter whose schema says `date-time` must be an RFC 3339 timestamp (date, `T`, time with seconds, optional fraction, `Z` or an offset; no looser form), the refusal naming the parameter and the format; no refusal holds the value; `orderBy` stays checked by Langfuse; tests prove each.
- Filter scan (#183, ADR-0010 and ADR-0012 amendments): where the deployment's version does not serve `traceId` of `scores_get-many` or `level` of `legacy_observationsV1_getMany` (the closed list `catalog.ScannedFilters`, exactly two `(operation, parameter, row field)` pairs; whether a pair qualifies is never decided from a payload), `execute_read` reads the list without the filter and keeps the rows whose field equals the value, instead of refusing it. The call is checked as if the deployment served the filter (`Operation.Scan`), so the value gets the type, enum, bounds and control and invisible character checks of a sent one, before any request; a `page` together with the filter is `invalid_argument`; a JSON null filter is no filter. The scan (`internal/workflows/filterscan.go`) reads from page 1 at `MaxLimit` rows a page whatever `limit` the call names (checked, then replaced) for at most `MaxScanPages` (10) pages, so no argument raises the page limit, through the one client (rate limit, concurrency cap, retries), and the audit line counts every request. Each page is sanitized and redacted before its rows are compared, so a row is matched as the agent would read it and comes back only as data inside the envelope, through clipping and the result size cap (the truncation hint names a time window, never a lower `limit` or paging). The result is page-shaped, `meta.filterScan` holds static text and numbers (`appliedBy`, the catalog's parameter and row field name, `complete`, `pagesRead`, `rowsRead`, `rowsExist`, `rowsMatched`), never the value or payload text, and none of Langfuse's pagination metadata. A failed page, or an answer that is not a page of row objects, ends the scan with its tool error and no rows. The scan ends where `meta.totalPages` says the list ends, else at the first empty page (never at a short one, which a smaller page size would also give), so a partial answer is never called complete. The rows are compared after redaction and the value as it was sent, so a value that holds a Langfuse key or a bearer token matches nothing. `describe_operation` lists the served parameters in `parameters` and, apart from them, the filter the server applies itself in `scannedFilters` (#199; `Operation.ScannedParams`): present only when the operation has a pair in the closed list and the version detected at startup does not serve that parameter, so a version text that is not a plain version means no entry, and never decided by an argument, a payload or a client (two clients of one server get the same description); an entry holds the facts of a parameter read from the catalog (`name`, `in`, `type`, `format`, `enum`, bounds) and a `note`, static text compiled into the binary, the same for every entry apart from the page limit of the scan, with no caller input, no Langfuse data and no spec text other than the parameter's own name and allowed values, which the catalog cleaned at load; the text content shows the same after the parameter list under a line of its own, and the output schema declares the key and says the note is static text written by this server; the description with it fits the smallest result size cap, whole. Every hint of `execute_read` that lists the operation's parameters (an unknown parameter, a parameter not served, a bad value, `limit` out of range, `page` together with the filter) adds one static clause after that list, only on a deployment that scans the filter; it holds the filter's catalog name, never a name or value of the call. Tests prove each.
- Timeouts, concurrency cap and rate limit (one shared per process, retries included, set only by `LANGFUSE_MCP_RATE_LIMIT`/`LANGFUSE_MCP_MAX_CONCURRENCY`; unset, the rate limit defaults by host: 30/min on an exact Cloud host, 1000 elsewhere, an explicit value always wins, #47), max response bytes read, max tool-result bytes returned (the result size cap: clip the largest string values (#177: each keeps its start and ends in the static marker `… [clipped]`; the floor is 128 bytes; a result that fits is untouched), then leave out rows of the payload's list of rows (a page's `data`, or the largest list of an object, by the bytes of its JSON, nested objects included) at a row boundary only if that is not enough, never clipping a continuation cursor, saying `truncated` with a static hint built from the parameters the operation takes, never from payload text; clipping runs after sanitizing and redaction; default 64 KiB, set only by `LANGFUSE_MCP_MAX_RESULT_BYTES`, an integer 16384 to 1048576 from the environment or the config file, environment wins; any other value stops startup naming the variable and its source, never the value; no tool argument reaches it, and a host may have its own lower limit for showing a result; applies to every tool result, workflow tools included; the discovery tools return catalog text, which is reduced by shape and never cut at a byte, #190 (see "Discovery" below); tests prove it); default and cap `limit` on list operations (the hint of a `limit` out of range, that of a `response_too_large` and the truncation hint of a page that lost rows name only the way of paging the operation has, static text, catalog parameter names and numbers, never a value, #193; the truncation hint, the hint of a `response_too_large`, and the hint of a `timeout` or `canceled` call name `fields` and its field groups, from the compiled list the guidance is built from, only for an operation that serves `fields` on the deployment, and never for `get_trace_tree`, which takes no such argument, #194; the same three hints name a lower `limit`, a shorter time window and, for the two metrics operations, their query JSON, from one compiled source (`sanitize.Remedies.NarrowWays`), only for an operation that takes them on the deployment, so they cannot name a way the others lack; a time window is a parameter of the closed list `timeWindowParams` in `internal/catalog` (the `from...`/`to...` pairs of the twelve operations that take them), served on the deployment, never any `date-time` parameter and never decided from an argument, a value, a payload or a client: the `startTime` of `legacy_observationsV1_get` and the `version` of `datasetItems_list` are on the closed list `notTimeWindows` (#204), a test fails, naming the operation and the parameter, when a `date-time` query parameter of the union catalog is on neither list or on both, and the value check of a `date-time` parameter (RFC 3339, before any request) covers every one of them, a window or not; an operation with no way of narrowing gets fixed text that says so and sends the agent to tell the user, not to call again; `get_trace_tree` gets fixed text per source for a timeout or canceled call, naming `execute_read` with the operation it reads; a failed filter scan names neither a lower `limit` nor paging; a failed write keeps its not-retried note and names a way after it only if the write operation takes one; the hint of a call held by the server's own limits is unchanged; none of these hints holds a value of the call or text of a Langfuse answer, and no argument selects its words, #203), and `config.row_limit` in the metrics `query` JSON (default 100, refuse outside 1..1000; the JSON is bounded to 16 KiB and depth 10, known top-level keys and their types only, re-encoded before it is sent). The metrics query guidance `describe_operation` gives on the `query` parameter of `metrics_metrics` and of `legacy_metricsV1_metrics` and the hint of a refused metrics query are static text whose key list is the validator's own, and never contain the query (#104, #178); tests prove it.
