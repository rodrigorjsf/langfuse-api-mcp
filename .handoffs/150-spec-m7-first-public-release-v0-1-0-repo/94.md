## What was built
Option 2 of the ticket. A Langfuse version is parsed in one place and the supported floor is defined once, both in the catalog module:
- `catalog.IsPlainVersion(s)`, `catalog.BelowSupportedFloor(s)` and `catalog.SupportedFloor` ("3.0.0") are exported; the single `versionPattern` stays in `internal/catalog/resolve.go`.
- `langfuse.DeploymentProfile.KnownVersion` and `detectVersion` use them; the `langfuse` regex, the `strings.Cut` major parse and `supportedFloor = 3` are gone.
- `cmd` builds its "below the supported floor" log text from `catalog.SupportedFloor` (second issue comment).
- `catalog.Resolve` clamps to the constant floor instead of the union's parsed `x-oldest-version`. `load` refuses a union catalog whose `x-oldest-version` is not `SupportedFloor`.
The two profile types stay as they are (option 1 is out of scope).

## Decisions & deviations
- The exported interface is two predicate functions plus a string constant. The `version` type stays unexported, which keeps the interface small. The cost is that `detectVersion` parses the version twice, which is negligible.
- The union's oldest version is replaced by the constant floor in `Resolve`, and `load` now checks that the two agree. With the embedded catalog (`x-oldest-version` 3.0.0), behaviour is identical. Edge case: a spec without `x-oldest-version` (only test specs and plain OpenAPI) now clamps a version below 3.0.0 to the floor and ignores families; before, it did not clamp. No test or production path hits it.
- The generator `scripts/gen-union-catalog.py` keeps its own `FLOOR = (3, 0, 0)` (Python, a maintainer script). The `load` check turns any drift into a startup and test failure. The comment on `SupportedFloor` names that `FLOOR`.

## Code review
Spec axis: no blocking findings.
- Generator FLOOR copy: documented in the comment on `SupportedFloor`; kept.
- Empty `x-oldest-version` edge case: dismissed. It affects only range-less test specs, and rejecting an empty value would break the plain-spec load tests.
Standards axis: fixed (a) the load test moved to `load_internal_test.go`; (b) the change-detector `SupportedFloor != "3.0.0"` assertion was dropped, since behaviour pins the floor; (c) `floor` is now parsed with `mustParseVersion`, which panics on a bad value; (d) the comment names the generator's FLOOR; (e) the stale "3.0.0" in the `Operation.Introduced` comment now refers to `SupportedFloor`; (f) the `load` control flow uses early returns. Dismissed: the double parse in `detectVersion` (small interface wins) and the overlapping test inputs (each test crosses its own seam).
