## Decisions & deviations

**npm trusted publishing (the basis of the third criterion).** Checked on 2026-10-12 against npm's documentation (https://docs.npmjs.com/trusted-publishers and https://docs.npmjs.com/generating-provenance-statements) and against the npm CLI the pinned Node ships. Node 24.21.0 ships npm 11.19.0 (nodejs.org/dist/index.json, and `npm -v` of the downloaded tarball). What npm asks of a GitHub Actions publisher and where `publish-npm` meets it:
- npm CLI >= 11.5.1 and Node >= 22.14.0: 11.19.0 and 24.21.0 (`NODE_VERSION` in `release.yml`, one pin for every `setup-node`).
- `id-token: write`: the job has exactly that permission.
- GitHub-hosted runner: `ubuntu-latest`.
- Workflow file name on the publisher, case-sensitive: `release.yml`; optional environment `release`: the job's `environment`.
- `repository.url` of each package.json equals the repository: all seven packed packages carry `git+https://github.com/rodrigorjsf/langfuse-api-mcp.git`.
- Provenance is automatic for a public repository and package; the job also passes `--provenance`.
- The empty `NODE_AUTH_TOKEN` (the `NPM_TOKEN` secret was deleted): npm 11.19.0's `lib/commands/publish.js` calls `oidc()` (line 147) before it reads credentials (line 149), `lib/utils/oidc.js` does not look at an existing `_authToken` and, on a successful exchange, overwrites it. An unset `${NODE_AUTH_TOKEN}` in `.npmrc` stays a literal in `@npmcli/config/lib/env-replace.js` (no error). So an empty value does not stop OIDC. One third-party write-up (dev.to) says it does; npm's source for 11.19.0 does not support that, and only a real publish settles it. **The line was kept on purpose**: wizard stage 8 (token fallback) re-runs the failed job, which runs the workflow as tagged; without `secrets.NPM_TOKEN` in the tagged workflow the fallback could not work. The old advice "remove that line if npm asks for a token" is gone from the doc and the workflow comment. `release.yml` was changed in comments only.
- Two npm-side settings the repository cannot show, found in the docs and put into wizard stage 5 and the doc: a trusted publisher whose first successful publish does not happen within 2 days of its creation expires ("must complete its first successful publish within 2 days"), and a publisher created after 2026-09-03 allows only `npm stage publish` until direct `npm publish` is allowed on it too, while the workflow runs `npm publish`. The seven publishers were created after `v0.1.0` (2026-09-30), so both can bite: this is the likeliest cause of a stage 8 run. npm checks nothing when a publisher is saved.

**Wizard choices.**
- Tools checked in stage 1: the ticket's `git gh jq cosign node npx`, plus `npm` (stage 10 runs `npm audit signatures`) and `curl` (the anonymous GHCR check, the Registry entry). Also checked: `origin` is this repository, git has a tagger identity, `gh` is signed in and an administrator, `gh attestation` exists (else it names `go install github.com/cli/cli/v2/cmd/gh@latest` and `https://cli.github.com`).
- Stage 2 is generic: it lists the exit-check tickets (`RELEASE_EXIT_ISSUES`, default `183 184 185`) with their state and the newest report of each campaign in the checkout. Stage 3 asks for the pull request number (lists the open ones); it never merges and verifies the merge commit is on `origin/main`. `RELEASE_MILESTONE` and `RELEASE_SPEC` default to this release's. A different release sets them.
- Stage 4 uses `gh run list -w ci.yml|release.yml --commit <origin/main>`; because CI starts no run for a docs-only change, a missing CI run falls back to the latest CI run on `main` and only a successful one is accepted. Stage 6 refuses to tag if `origin/main` moved since stage 4.
- Stage 7 finds the run by `headBranch == <tag>` (the push of the tag, not the earlier push to `main` on the same commit). Stage 8/9 re-run exactly one job (`gh run rerun --job <id>`: the job and the jobs that depend on it), not `--failed`, so the confirmation names what runs.
- A re-run of the wizard after the tag stops in the preflight by design (the ticket's "tag exists neither locally nor on origin"); the doc has the manual continuation. A trap tells the maintainer, on any exit, that `NPM_TOKEN` is still stored (with the delete command) and, after the tag, to continue by hand.
- `ENV_FILE=/dev/null` so the library neither reads nor writes any file; `write_env`/`set_secret` are not called. The transcript and the downloads live in a `mktemp -d` directory (mode 700). The Langfuse public key is also read hidden (the project redacts `pk-lf-` as a credential).
- Marked `(unverified)` in the stages, because the agent could not check them against the live services: the npm package settings address (`https://www.npmjs.com/package/<pkg>/access`; npm's docs say Settings > Publishing access), the npm token menu wording, the GHCR package settings path, `gh run rerun --job` semantics (the REST endpoint re-runs the job and its dependents), the `continue-on-error` re-run of `publish-registry`, and the Registry search response shape (taken from the `v0.1.0` record).

**Deviations.** None from the criteria. The docs name `v0.2.0` as the current release before the tag exists (the ticket asks for exactly that): between the merge of the spec's pull request and the tag, `go install ...@v0.2.0` does not resolve; the wizard's stages 3 to 6 are meant to be run in one sitting.

## Learnings

- Docker Desktop on WSL2: `docker run --network host` reaches the VM's loopback, not the WSL one; the container smoke needs CI.
- `actions/setup-node` v7 exports `NODE_AUTH_TOKEN` only when the workflow sets it; npm 11 leaves an unset `${NODE_AUTH_TOKEN}` in `.npmrc` as a literal.
- npm trusted publishers expire 2 days after creation without a first publish, and ones created after 2026-09-03 need "npm publish" allowed explicitly (docs.npmjs.com/trusted-publishers).
- `go install github.com/goreleaser/goreleaser/v2@v2.18.2` and `.../syft/cmd/syft@v1.52.0` into a scratch `GOBIN` give a full local snapshot in about 5 minutes; `RELEASE_VERSION=X.Y.Z` makes it build the version a tag would give.
- This machine's `npm` is broken (`Cannot find module .../npm-cli.js`); a Node tarball from nodejs.org in scratch works.
- A text test of a shell script must read warning lines from the raw file, not from the code-only view.
