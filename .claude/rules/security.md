**Credentials**
- Langfuse keys come only from the server's environment/config — never from tool arguments, never forwarded from the MCP client (no token passthrough). Langfuse keys cannot be read-only, so the server is the only write gate for calls through the server; keys in the agent's own environment bypass it (#146).
- The config file (ADR-0011) must never hold keys: reject `LANGFUSE_PUBLIC_KEY`/`LANGFUSE_SECRET_KEY` found there (any spelling, after `export` and any blanks, #156) with a startup error; tests prove it.
- An unknown config-file key only draws a startup warning naming file, line and key (escaped, cut to 64 runes), never its value (#26); tests prove it.
- Redact `Authorization`, `sk-lf-…`, `pk-lf-…`, the HTTP bearer token and proxy credentials (`user:password@` in a proxy URL; used only for Basic proxy auth, logged as `scheme://host:port`) from logs, errors, hints, the audit line and tool output. A startup error for an invalid proxy value names the variable and its source, never the value.
- Langfuse keys, where a key starts (#208, #210): the key characters (`A-Za-z0-9_-`) after `pk-lf-`/`sk-lf-` are replaced by `[REDACTED]` when the prefix stands at a word boundary, directly after a JSON escape written as text, or directly after a place where the cleaning removed something. The escape: one or more backslashes, then `b`, `f`, `n`, `r` or `t`, or `u` and four hexadecimal digits. That is how a line feed reads inside a string that holds JSON text (the Observations v2 `input` and `output`, stringified once or more: one backslash and `n`, two, four), where the letter of the escape is a word character and no boundary stands before the key. The escape stays character for character, so a string that held valid JSON text still does, decoding to the same value with the key replaced. The rule on text reads the text only and is compiled into the binary: it decodes nothing and counts no backslashes, so a literal backslash and a letter before a key (`C:\nsk-lf-…`, or an escaped backslash and `nsk-lf-…`) is taken for an escape too, an over-redaction accepted; no payload, argument, parameter, Langfuse answer or client changes it or turns it off. The same pattern serves every place a key is redacted (payload strings and keys, Langfuse error text, the names an error echoes, the confirmation text, the audit line, the last pass over a result), always before a cut; a text without `k-lf-` skips it. The removed place (#210): wherever the redactor cleans a text itself (`Redactor.Redact`, `sanitize.Payload`), a place where `sanitize.Text` removed an invisible, bidirectional or control character, or a whole terminal escape sequence, is a boundary of its own, whatever stands before it (`textPlaces` records the places, `redactKeysAfterPlaces` reads them): `token`, a zero-width space and `sk-lf-…` come back as `token[REDACTED]`, `x`, a bell and `sk-lf-…` as `x[REDACTED]`, and a word split right before the prefix by a hidden character (`ta`, a zero-width space and `sk-lf-name`) is redacted too, an over-redaction accepted; `task-lf-name`, where nothing was removed, stays; a key that a place splits is found whole, as before (the text is cleaned first). Inside a string that holds JSON text (below, "Tool results") the strings are decoded first, so the escape of a character the cleaning removes (`x\bsk-lf-…`, `x\u200bsk-lf-…`, `x\u001b[31msk-lf-…`) is a removed place too, and a key split by such an escape (`sk-lf-abc\u200bdef-…`) is redacted whole; the escape of an ASCII letter, digit or underscore before a key (`x\u0041sk-lf-…`) would glue the key to a decoded letter, so `redactKeysAfterLetterEscapes` redacts it in the text before it is decoded, the escape kept while the text is not written again. Not redacted, each a case of its own, documented and tracked: a key glued to an ASCII letter, digit or underscore that is really there (`xsk-lf-…`, `KEY_sk-lf-…`; a word that only holds the prefix, `task-lf-name`, stays as it is; a maintainer decision, #211). The same key after a line break that the confirmation text drops, because `sanitize.Line` runs before the redactor reads the body summary (#211). In text that is not decoded (a string that is not exactly one JSON value, another notation of a character such as `\x1b`, a fifth level of JSON text), a key split by a control or invisible character written as an escape, which is redacted only up to the escape: the text of the escape and the rest of the key stay. Tests prove each.
- Header credentials inside Langfuse data (#180, #196): the token of a credential under an `Authorization` name or after `Bearer` is replaced by `[REDACTED]` and the scheme stays (`Authorization: Bearer [REDACTED]`, `{"Authorization": "Basic [REDACTED]"}`). A scheme is a letter, then letters, digits and `_ . + -`. A token is a run of at least 16 printable ASCII characters other than space, `"`, `'`, `` ` `` and `\` (`minTokenLength`, kept above the 10 characters of `[REDACTED]` so redacting twice changes nothing); it ends at the first other character, so a closing quote or a JSON escape ends it, and a credential holding such a character (or a non-ASCII one) is redacted only up to it, if that part has 16 characters. One name rule, compiled into the binary and never changed by a payload or an argument, serves every form (`isAuthorizationName` for the object form, the patterns of the other two encode the same rule, and the tests walk one list of names through all three): a name counts when, with invisible and control characters stripped, surrounding blanks dropped and case ignored, it is `authorization` or ends in `authorization` after a character that is not an ASCII letter or digit (`Authorization`, `Proxy-Authorization`, `X-Upstream-Authorization`, `http.request.header.authorization`, `HTTP_AUTHORIZATION`); a name that only contains the word (`authorizationMode`, `authorization_url`, `reauthorization`) does not. Three forms: (1) the plain form `<name>: <scheme> <token>`, blanks (spaces or tabs) around the colon and at least one before the token, and `Bearer <token>` anywhere, `bearer` in any case at the start of a word; (2) the object form, in `sanitize.Payload`: in every JSON object of a payload, at any depth, the value of a member whose key counts is redacted when it is a string `<scheme> <token>` (blanks before the scheme allowed) or a list, each string item of which is checked the same way; the key, the siblings and the rest of the value stay, a value of another type stays, and of two keys that read the same once cleaned the kept value is the redacted one; (3) the quoted text form, inside any string the redactor reads: a quoted name that counts, a colon and a quoted value `<scheme> <token>` (or the first item of a list), the quotes `"` or `'` each written as itself or as a JSON escape (one or more backslashes before it), spaces, tabs and line breaks around the name, around the colon and after the bracket of a list (a pretty-printed map matches; a line break written as an escape does not): the JSON text of a header map, escaped once or more, or a Python dictionary printed as text. The shape is all it checks: a long word or a URL right after `Bearer`, or after a word that reads as a scheme under such a name, is taken for a token. Not redacted: a shorter token, prose with short words after the keywords, a value with no scheme under such a name (`{"Authorization": "<token>"}`), a header written as a name and value pair (`{"name": "Authorization", "value": "Basic …"}`, a list of two-item lists), a value that is an object, the items after the first of a list in the quoted text form (inside a string that is decoded as JSON text, the object form reads the list and every string item is redacted), a line break written as an escape between a name and its value, and any other header or secret format (cookies, API key headers, query-string tokens). It runs wherever a key is redacted, always before a cut: every payload string and key (before clipping), Langfuse error text (before 500 runes), the operation ID, parameter name and argument name an error echoes (before 64 bytes), the body summary of a confirmation (before 300 runes), the audit line, and a last pass over each result's JSON text. Invisible and control characters are stripped before matching, so a token split by them is found, and are gone from a text that held a secret; tests prove each.
- After startup the key pair travels only as `langfuse.KeyPair`, which renders `[REDACTED]` in fmt, JSON and slog; never copy the keys into plain `string` fields.

**Write gating** (ADR-0003 and its amendment)
- `execute_read` accepts GET operation IDs only. `execute_write` is not registered unless `LANGFUSE_MCP_ALLOW_WRITES=true` (exactly `true`/`false`, environment or config file, environment wins; any other value stops startup naming the variable and its source, never the value). Tests must prove both.
- The tool set is fixed at startup; it never changes per request or per client.
- While write mode is off no tool tells a write operation ID from one that is in no release (#192): `execute_read` and `describe_operation` answer it `operation_not_found` in the words and with the hint of an unknown ID, naming no HTTP method, echoed only redacted, stripped, quoted and cut to 64 bytes, and sending nothing. In write mode `execute_read` keeps `invalid_argument`, naming the method and pointing to `execute_write`. An excluded operation keeps its answer. The tool descriptions and schemas are the same in both modes, so they name no write operation ID. Tests prove each, with every write operation of the catalog walked.
- `execute_write` (#110): an excluded, unknown or read `operationId` is `operation_not_found` (an unavailable `operationId`, #174, is `operation_unavailable` in every tool that takes one, whatever kind of operation the tool runs: `execute_write` says it of an unavailable read operation and, in write mode, `execute_read` of an unavailable write operation; a write operation ID while write mode is off stays `operation_not_found`), echoed only redacted and cut to 64 bytes; path and query parameters get the `execute_read` checks; the body must be a JSON object where the schema expects one, at most 256 KiB compacted and 32 levels deep, and absent where the operation takes none, refused with `invalid_argument` naming the rule, never the value, before any request; then (#112) it is validated against the operation's JSON Schema 2020-12 for the deployment's version (#202, below), compiled once, and a failure is refused with `invalid_argument` naming only the JSON location (built from schema property names and array indexes, never a caller's key) and the failed keyword, never a value; unknown keys are refused where the schema forbids them. The body is the one of the version detected at startup (#202, ADR-0012 amendment): the union catalog keeps every distinct body the release specs gave the operation, each with the releases it holds for (`x-request-bodies` with `x-spans`; an operation the server never offers, ADR-0004, keeps its newest body only, `x-newest-body-only`, and load fails if an operation the server offers is marked so), `catalog.Resolve` picks the body of the newest release not newer than the deployment (the newest when no version was detected), and `describe_operation` returns it and `execute_write` checks against it, in full at every cap; nothing a Langfuse answer says, no argument and no client selects a body, so two clients of one server get the same schema; a refusal names the JSON location from that schema's own property names, never a caller's key or value, its hint names no release, and a property only another release has is an unknown key where this schema lacks it; the size, depth, object, absent-body checks and the confirmation come first and are unchanged under every body; only the bodies a version chooses are compiled, a schema that does not compile stops startup (`Catalog.BodyError`) and a body is never checked against it; every stored body, the older ones too, is stripped at load, compiles, has no property named like a credential and, reduced, fits the smallest result size cap. In write mode `describe_operation` returns the body schema (stripped at load, framed as third-party text), a `destructive` flag and, for `comments_create` and `scores_create` only, a static `body.guidance` (#192), and `search_operations` gives every write line its HTTP method and `destructive`, the value `describe_operation` returns (#192). Every destructive operation (DELETE, PUT, PATCH) runs only after the user confirms that exact call (#113, ADR-0003 amendment): after its parameter and body checks, the server asks through form elicitation with a multi round-trip request (`InputRequests` + a `RequestState`; older-protocol clients go through the SDK middleware, same handler path). The state is `<expiryUnix>.` + base64url(HMAC-SHA256(key, `<expiryUnix>|<operationId>|` + the checked request re-encoded deterministically)), the key 32 `crypto/rand` bytes drawn at startup, never logged or persisted; it expires after 5 minutes and is compared with `hmac.Equal`. Fail-closed, nothing sent: no form elicitation (per-request capabilities) → `confirmation_unavailable`; decline or cancel → `confirmation_declined`; an accept without a valid state (sent on the first call, other arguments, forged, corrupted, expired, another process's key) → `confirmation_invalid`. No setting skips it. The confirmation text names the operation ID, method, path and query parameters and a body summary cut at 300 runes (saying so, with the body size in bytes), the trace ID count for `trace_deleteMultiple`; every argument-derived string is stripped of control, invisible and bidi characters, redacted and shown quoted, markup as text (not escaped: the elicitation message is plain text per MCP, so markup rendering is the client's). Replay of the identical call within the expiry is not prevented (every confirmed method is idempotent). POST creates run without a server confirmation. A write is never retried. Its audit line is logged at `Warn` with `confirmation` and never the body. Excluded from the catalog: `media_getUploadUrl`, `media_patch`, `llmConnections_upsert`, `blobStorageIntegrations_upsertBlobStorageIntegration`; a catalog test fails on any property whose name contains `secret`, `password` or `accessKey` in any stored body of an in-scope write operation, whatever release it is from (ADR-0004 amendment). Tests prove each.

**Tool results** (LLM01:2025/2026, MCP06:2025)
- Langfuse payloads are untrusted data: wrap them in a labelled envelope; strip invisible/bidi Unicode (U+E0000–E007F, zero-width, bidi overrides, variation selectors and other default-ignorable code points, #156) and control chars; a terminal escape sequence goes whole, not with its escape character alone (#193): wherever the server strips control characters from Langfuse data (`sanitize.Text` for every payload string and key, the audit line and a confirmation, `sanitize.Message` for error text taken from Langfuse), a CSI (ESC `[` or U+009B, parameter and intermediate bytes, one final byte; the U+009B form, the only one that can stand raw in the JSON text of a result, also ends its scan at a quote or a backslash, so it never takes the quote or the backslash of a JSON string) and an OSC (ESC `]` up to BEL or ESC `\`, an OSC 8 hyperlink with its URL) are removed with the rest of the sequence, by a scan of at most `sanitize.MaxEscapeSequenceRunes` (256) characters from the escape character; an escape character that starts no complete sequence within them goes alone and the text after it stays, so no payload makes the sanitizer drop more than that; text with no escape character before it (`[31m`) is never changed; each JSON string is cleaned alone; the removal runs before redaction and clipping, so a key behind or split by a sequence is still redacted and the cap counts the cleaned text (the embedded OpenAPI text of the catalog is not Langfuse data and keeps its own load-time stripping); JSON text inside a payload string (#210): a payload string that, once cleaned as above, is exactly one valid JSON value that is an object, a list or a string, with nothing but JSON blanks around it, is decoded, and its value is cleaned as a payload is (every string and key by `sanitize.Text`, a terminal escape sequence whole, each string redacted after its cleaning, a key that reads the same as another only once cleaned never shadowing the clean key, the object form of a header credential); a string of that value that is itself JSON text is cleaned the same way, down to `sanitize.MaxJSONTextLevels` (4) decodings below the payload string, and a string reached after that many is cleaned and redacted as plain text, its escapes kept. This is how the Observations v2 `input` and `output` (JSON text in a string) lose a control or invisible character written as an escape, which a client that parses the text would get back. Text cannot tell the escape of a character from the same letters written on purpose, so the string is decoded, not searched: a Windows path (`C:\\build` in the text) and `\\u001b[31m` with the backslash itself escaped decode to the letters and stay. The text is written again only when the cleaning changed its value: then it is the cleaned value written as a payload is (compact, keys in sorted order, numbers as written, a repeated key once with its last value, HTML left alone), with U+2028 and U+2029 kept as characters so that the text is never longer than it was apart from `[REDACTED]` standing for a shorter secret; otherwise it comes back byte for byte, pretty-printed or not. The order: the outer string is cleaned (so a raw invisible character cannot hide a JSON text from the decoder), each level is decoded and cleaned before it is redacted, then the text is redacted as before, and clipping stays last (a clipped JSON text is cut text, not decoded). Not decoded, so not cleaned of escapes, each documented: a string that is not exactly one JSON value (JSON text followed by prose, cut JSON, two values in a row, a Python dictionary printed as text), another notation of a character (`\x1b`, `\033`) and a fifth level; the letters of an escape stay there. Each level reads its string once more, so the work stays in proportion to the size of the payload, and no payload makes the result longer than twice itself, which the outer writer's escapes of U+2028 give today; the level bound is a constant of the binary and no setting, argument, payload or client changes it or turns the rule off; the work added to a string that does not start with a brace, a bracket or a quote is one byte read (`BenchmarkPayload`); tests prove each; never render HTML/Markdown from them; never echo them unescaped into error text. A proxy's CONNECT answer (status reason, body) is untrusted too: it is dropped, never echoed into an error, hint or audit line (#32).

**Transport**
- stdio: logs to stderr only. It offers no protocol from 2026-07-28 (#145), and it reads no byte of stdin until the session has recorded that (#191): go-sdk v1.8.0 starts reading inside `Server.Connect` and records the transport's protocols a few instructions later, so a `server/discover` probe already waiting in the pipe, as Claude Code leaves it during a slow startup, could be answered with 2026-07-28 and stored as the session's `initialize` parameters, and the legacy `initialize` after it refused as a duplicate. A probe therefore never negotiates a session, however early it arrives, and is answered with the older protocols only; a session is negotiated only through the legacy `initialize`; neither the client capabilities of a handshake, nor a probe sent before, between or after the `initialize` messages, nor a second `initialize` change the tool set or the write gate, and a malformed `server/discover` is refused without dropping the connection; tests prove it, with the probe forced to be handled inside the SDK's window. Both workarounds go once go-sdk accepts a legacy `initialize` after a probe and records a transport's protocols before it reads the first message (#162). HTTP (opt-in, **Planned**, #160; stdio is the only transport today): bind 127.0.0.1, require a random ≥256-bit bearer token compared in constant time, validate `Origin` (403 on invalid) and `Host` (loopback only), answer session GET/DELETE with 405.

**TLS** (ADR-0006): system pool + explicit/ambient CAs appended in code; `SSL_CERT_FILE`/`SSL_CERT_DIR` are captured and removed from the environment before anything loads certificates (proven by `TestExecutableTrustsTheOSStoreAndAmbientCAsAtOnce`); `MinVersion` TLS 1.2; no skip-verify option exists.

**Audit**: one structured stderr log line per tool call (tool, operationId, method, status, latency, bytes, requests: the Langfuse requests the call made) — metadata only, never payloads, and the cause of a request that got no answer never holds the request URL or a refused redirect's target (#156); an `execute_write` line is at `Warn` and adds `confirmation` (`not_required`, `requested`, `accepted`, `declined`, `unavailable`, `invalid`).
