## What was built
An operator sets the result size cap with `LANGFUSE_MCP_MAX_RESULT_BYTES` (environment or config file, environment wins; plain decimal integer 16384 to 1048576; unset means 65536). The default drops from 100 KiB to 64 KiB. An invalid value stops startup with an error naming the variable and its source, never the value. The startup log has a `result size cap` line (`bytes`, `source` = default / environment / config-file). The cap applies to `execute_read`, `execute_write` and `get_trace_tree` results (the ones carrying Langfuse data); no tool argument reaches it.

## Decisions & deviations
- `sanitize.Wrap(op, payload, limit)` and `WrapWith(op, payload, limit, hint, cutHint)` take the cap; `sanitize.MaxResultBytes` became `DefaultMaxResultBytes = 64 KiB`. The server takes it through `server.WithMaxResultBytes(n)`; `cmd` always passes the config-validated value. Config and sanitize each hold the 64 KiB default (config may import nothing internal); both are proven by tests.
- The cap-parser is strict (ASCII digits only; no sign, unit, separator, exponent) and never echoes the value, unlike the older `loadLimit`, which quotes an environment value. Left `loadLimit` unchanged (out of scope).
- Discovery tools (`search_operations`, `describe_operation`) are NOT cut: they return catalog text, and cutting a body schema would make it misleading. In write mode `describe_operation` of `unstable_evaluationRules_create` is about 37 KB, so a cap below that does not bound it. Docs state this; filed as #190.
- Absorbed test fix (commit b1f6145): four tests were already red on BASE_SHA because the union catalog was regenerated up to v4.50.0 (#169) but counts and one expected ID list still described 4.46.0 (119 -> 120 operations, 68 -> 69 GET, `unstable_skills_getFileContent` replaced by `getFileContents` at the newest version).
- Existing tests that asserted the old 100 KiB limit now assert 64 KiB.
