## What was built
- A parameter whose schema has no `type` now has its spec-given bounds checked, based on the JSON kind of the value the caller passed. A number is checked against `minimum`/`maximum`. A string is checked against `minLength`/`maxLength`, counted in runes. A boolean is not checked against any bound. This applies to list items too.
- The kind is taken from the raw value before rendering. So a numeric-looking string such as `"999"` is checked for length, and a long number such as `1.25` is not.
- A refusal still wraps `ErrInvalidParameter` (`invalid_argument`) and names the bound, never the value.
- New data-driven `execute_read` test: it drives every spec-given bound of every read operation in the embedded union catalog through the server. It skips today because no such bound exists; it runs with no edits once a regeneration brings one.

## Decisions & deviations
- **Server-seam proof uses a data-driven test over the real catalog, not a fixture catalog (option 3).** A fixture catalog would need new exported catalog API that only tests use. The data-driven test is the ticket's option 1, automated: it fires in the first regeneration PR that brings a bound.
- **Option 2 was implemented now.** The ticket recommended waiting until an untyped bounded parameter appears. It was built now because AC2 asks for the behaviour.
- **Raw items and rendered values stay aligned through a shared `listItems` helper**, used by both `Param.values` and `Param.inBounds`.
- **`outOfBoundValues` generates only bounds the schema's type can meet.** It emits no numeric case for a string type and no length case for an integer or number type.
