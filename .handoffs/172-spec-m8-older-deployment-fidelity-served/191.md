## What was built
Over stdio, a `server/discover` probe never negotiates a session, however early it arrives. `transport.Stdio` now connects the session itself with stdin wrapped in a reader that waits, and opens it once `Server.Connect` has returned, that is once the SDK has recorded the protocols stdio offers (go-sdk v1.8.0 starts the read loop first and records them a few instructions later; a probe already in the pipe could be handled in between, answered with 2026-07-28 and stored, and the host's `initialize` refused as a duplicate). It is Direction 1 of the ticket: the probe's answer is unchanged (a result without 2026-07-28), so no host-side behaviour changes. A regression test forces the SDK's order of events instead of waiting for it. The docs, the code comment and the research record say what is true after the fix; #162 has its comment.

## Decisions & deviations
- **Fix = Direction 1** (hold the first read until the session has recorded its protocols). Directions 2 and 3 change the probe's answer (an error, or code that knows the protocol) and Claude Code's reaction to an error is unverified; Direction 1 does not need that check. `Server.Run` is not called any more: `Stdio` calls `Connect`, opens the reader, and waits for the session as `Run` does (12 lines; justified in the doc comment). The gate sits in the reader (`mcp.IOTransport` over a `heldReader`), not in a wrapped `mcp.Connection`, because the SDK's connection has an unexported optional `sessionUpdated` interface that a wrapper would hide.
- **Forcing the order without waiting for it.** Nothing a test can do from outside the SDK runs inside the window: `filterSupportedVersions` and `SupportsProtocolVersion` run while `Connect` holds `ss.mu`, after the window. So the test edits a temporary copy of go-sdk (module cache and `go.mod` untouched; `go build -overlay` cannot replace module-cache files). Any hold that waits for "the probe was handled" is, by design, never satisfied by a correct server (the fix makes it impossible), so the hold has a 3 s bound: it is reached only by a correct server, the failing path is signal-driven and deterministic, and a faulty server that handled the probe later than 3 s would pass (accepted; the SDK's window is microseconds). Each case against the edited build therefore takes ~3 s. This is documented in the test, CONTRIBUTING.md and `testing.md`.
- **Anchors.** The test edits two exact lines of go-sdk v1.8.0 `mcp/server.go` and fails naming the anchor if a go-sdk upgrade moves one.
- **Observation, not filed:** a first `initialize` with wrong types is refused by the SDK with a message that quotes the client's own parameters (`handling 'initialize': unmarshaling "{...}"...`); it goes only to the client that sent them, never to stderr, and changes nothing. The spec's static-text rule is about probes (checked); I did not assert it for `initialize` and made no claim about it in the docs.
- The probe answer, startup order (detection first, then stdin) and the fixed tool set are unchanged.

## Learnings
- go is not on the bash PATH here; the 1.27.1 toolchain is at `~/go/pkg/mod/golang.org/toolchain@v0.0.1-go1.27.1.linux-amd64/bin` (use with `GOTOOLCHAIN=local`).
- `go build -overlay` cannot replace files under GOMODCACHE; copy the module, edit the copy and build with `-modfile=<alt.mod>` (`go mod edit -modfile=... -replace=...`, with a copy of `go.sum` next to it).
- A race in a third-party library that lets the code under test run in a microsecond window can only be forced by editing that library in a temporary copy; a hook inside `SupportsProtocolVersion` is too late (it runs under the lock the handler needs).
- `pkill -f <pattern>` kills your own shell when the pattern appears in the command line.
- The file-writing tool turns `\uXXXX` in file content into the real character; check with `grep -P` / `gofmt -l` (a BOM in Go source is an error).
- The race suite of `internal/server` can be proven on this machine with a script that builds `go test -race -c` once and runs the test list in 8 round-robin chunks (`GOGC=50 server.test -test.run '^(a|b|...)$' -test.parallel 6`), as in #188's handoff.
