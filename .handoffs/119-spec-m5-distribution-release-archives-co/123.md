## What was built
- A user configures the server as `npx -y langfuse-api-mcp` and the Go binary for their platform runs. Nothing is downloaded at install time, and no package has a script.
- `packaging/npm/bin/langfuse-mcp.js` is the Node shim and the main package's only `bin` (`langfuse-mcp`). It resolves `langfuse-api-mcp-<platform>-<arch>` and spawns its binary with argv and env unchanged, `stdio: inherit` and `shell: false`. It forwards SIGINT, SIGTERM and SIGHUP, and exits with the child's code or re-raises its signal (falling back to 128+n). An unsupported platform gets an error naming it and the six supported ones. A missing platform package gets an error naming the package.
- `packaging/npm/pack.mjs` is the project's packaging script. It builds 7 packages from GoReleaser's `dist/artifacts.json` and `dist/metadata.json` and runs `npm pack`. Each platform package is restricted by `os`/`cpu` and holds only its binary. Every version equals the release version. The script fails if the shim's supported list differs from the built targets.
- `packaging/npm/smoke-registry.mjs` is a local read-only registry on 127.0.0.1 that serves the packed tarballs. With it, `npx` resolves the optional dependencies exactly as it will from npmjs.org.
- `release.yml` changes:
  - The snapshot job now packs the npm packages. A jq gate checks the versions, that there are no scripts and that there are 7 tarballs. The job uploads `npm-packages`.
  - A new `smoke-npx` matrix (ubuntu, macOS, Windows) runs the shim tests, then an npx install with `npm_config_ignore_scripts=true`. It checks that only this platform's package was installed, then runs S2 `TestInstalledArtifact` with `["npx","-y","langfuse-api-mcp@<version>"]`. The #102 retry is copied unchanged.

## Decisions & deviations
- A second test surface beside S2 (the spec says S2 is "the only new seam"). This is needed because npx intermediates signals and the platform cannot be changed through S2.
- The local registry script was added so the smoke proves npm's real optional-dependency resolution and `os`/`cpu` filtering. Installing the tarballs directly would force the platform choice. If the registry fails to start, the step fails; it never falls back to npmjs.org.
- Platform packages are unscoped (`langfuse-api-mcp-<platform>-<arch>`, Node platform/arch names), because a scope would need an npm org. Re-check the name availability in M7 together with the main name.
- The npx install is warmed once (`npm exec --package … -- node -e 0`) before the parallel S2 cases share the cache. `npm_config_cache` is set explicitly because S2 children get their own HOME/AppData.
- `cmd.WaitDelay = 5s` was added to the S2 launch helpers. On Windows, killing `npx.cmd` leaves the chain holding the pipes, and a failing smoke would otherwise hang until the job timeout.
- The shim tests run in the `smoke-npx` job, not in ci.yml. The release workflow path filter covers `packaging/**`.

## Learnings
- `node --test <dir>` fails on Node 24; pass the test file path explicitly.
- Local npm under `~/.local` is broken on this machine; use a Node tarball in the scratchpad.
- The S2 children override HOME/AppData, so npx needs an explicit `npm_config_cache`.
