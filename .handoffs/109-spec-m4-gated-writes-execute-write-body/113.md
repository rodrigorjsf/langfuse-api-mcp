## What was built
- `execute_write` now runs DELETE/PUT/PATCH after the user confirms that exact call. It checks params, then the body, then confirmation (the #110 order is restored).
- The first call returns `InputRequests` (an accept-only form elicitation under `confirm`) and a `RequestState`. That state is `<expiryUnix>.` + base64url(HMAC-SHA256(key, `<expiry>|<opId>|` + canonical args)). The key is 32 crypto/rand bytes per process. States expire after 5 min.
- Canonical args are the checked request re-encoded with sorted keys: escaped path, query, and body.
- Every refusal fails closed and sends nothing:
  - no form elicitation → `confirmation_unavailable` (per-request caps; none or URL-only both count)
  - decline or cancel → `confirmation_declined`
  - an accept without a valid state (first call, rebound, forged, corrupted, expired, another process) → `confirmation_invalid`
- Older protocols (2025-11-25) go through the SDK server middleware and use the same handler path.
- The confirmation text holds the op ID, method, path and query params (quoted, stripped, redacted), and a body summary cut at 300 runes with the size in bytes. `trace_deleteMultiple` gets a trace-ID count.
- Folder-name allow-list: added `prompts_delete`/`promptName`, `promptVersion_update`/`name` and `promptVersion_update`/`promptName` (<3.18.0), and `datasets_deleteRun`/`datasetName`.

## Decisions & deviations
- Audit `confirmation` values go beyond the spec's list (accepted/declined/not_required). They add `requested` (the ask round, which is its own tool call and its own line), `unavailable` and `invalid`. The field is absent when args are refused before confirmation starts.
- The confirmation text also lists query parameters. `prompts_delete` `version`/`label` change what is deleted, and they are bound by the MAC anyway.
- Markup is shown unescaped inside JSON quotes: `<b>` stays `<b>`, and `SetEscapeHTML(false)` is set. The MCP elicitation message is plain text, so escaping would show backslashes. This is documented in the README and security.md.
- When an InputResponses entry is present, the state is verified before the action is read, so a decline with a bad state gets `confirmation_invalid`. A state without InputResponses counts as a fresh call and gets asked again.
- The whole-catalog `TestExecuteWriteRefusesEveryDestructiveOperationWithConfirmationUnavailable` now accepts `invalid_argument` for ops whose sample `{}` body fails the schema. It still requires 20 or more `confirmation_unavailable` results and no request.
- The `datasets_deleteRun`/`datasetName` evidence is general: the docs say dataset names with slashes are URL-encoded in any path parameter. The same route (GET) fails upstream for Folder names (langfuse/langfuse#13933). README, the folderNameHint and the catalog comment all say so. The live test does not cover it.
- ROADMAP says "PR: the run-spec PR of spec #109" because the PR does not exist yet. The orchestrator should replace it with the URL.
- The confirm module was drafted before its tests. Its handler wiring came after the red run, which showed 18 failing tests.
- No advisor or rubber-duck pass was run, per the implementer rules.
