## What was built
A payload string that is exactly one JSON object, list or string (what Observations v2 returns for every `input` and `output`) is now decoded by `sanitize.Payload`, its strings and keys are cleaned and redacted as a payload is, and a string inside that is itself JSON text is cleaned the same way, down to `sanitize.MaxJSONTextLevels` (4) decodings. A control or invisible character, or a terminal escape sequence, written as a JSON escape in such a text is removed; a Langfuse key split by one is redacted whole; a header map in it is redacted as an object. The text is written again (compact, sorted keys, exact numbers, a repeated key once, U+2028/U+2029 kept as characters so it never grows) only when the cleaning changed its value; otherwise it comes back byte for byte. Separately, a place where the cleaning removed a character or a whole terminal sequence is now a boundary for the Langfuse key rule in `Redactor.Redact` and `Payload` (`token`, a zero-width space and `sk-lf-…` come back as `token[REDACTED]`). Through `execute_read` and both sources of `get_trace_tree` this comes with no change of their own.

## Decisions & deviations
- **Order inside a payload string** (`cleanString` in `jsontext.go`): `Text` (places recorded) -> key rule at the places -> if JSON text: letter-escape pre-pass, decode, clean each level, write again only if changed -> redact the text as before. Pass at the places runs before decoding because offsets are meaningless after a rewrite.
- **`redactKeysAfterPlaces`** finds keys only at the recorded places and leaves those `keyPattern` already finds to it, so `sk-lf-abc<ZWSP>sk-lf-def` stays one `[REDACTED]` as before. It runs before the configured-secret replacement (offsets).
- **Found while designing: a regression the ticket did not name.** The escape of an ASCII letter/digit/underscore before a key in JSON text (`x\u0041sk-lf-…`) was redacted by #208's text rule; once the text is decoded and written again for another change, the key would be glued to a real `A` and leak. `redactKeysAfterLetterEscapes` redacts it in the text before decoding (escape kept while the text is not written again). Tests `TestPayloadRedactsAKeyAfterTheEscapeOfALetterInJSONTextWhetherOrNotItIsWrittenAgain` (3 levels), `...OfABoundaryCharacterInJSONTextAndDecodesIt`. Left uncovered (documented as split-key in text that is not decoded): a key split by an escape right after such a letter escape.
- **Spec-review finding, fixed:** a value shadowed by a later repeated key was invisible to the walk (decoding into a map keeps the last), so a text with nothing else to clean returned it byte for byte, hidden characters and key tail included. Fix: `mayShadowSomething` (text holds `\u`, `\b`, `\f` or the word authorization) gates a token-by-token reading (`shadowedMembers`) that returns each dropped member as a one-member object; they are walked with the same function (so the header object form applies) and, if any changes, the text is written again from the kept values. A clean shadowed value keeps byte identity (`TestPayloadKeepsAJSONTextWithARepeatedKeyWhoseShadowedValueIsCleanByteForByte`). The reader needs no depth guard: it runs only on text that the standard decoder (depth 10000) accepted. This is a small second reader of JSON, which the brief said not to add for the cleaning walk; it exists only to find dropped members.
- **Existing expectations that changed** (say so in the PR): layout only — a header map with blanks inside a string that is JSON text is compact now (`TestAHeaderMapIsRedactedAtEveryDepthAndInEveryForm`, `TestAHeaderMapInAnObservationOfTheTraceTreeIsRedactedWhateverItsScheme`). By design — `keyescape_test.go`: the glued-after-invisible-character limit test now expects `token[REDACTED]` (renamed), and the M1 limit test is inverted (`TestPayloadRemovesAControlCharacterWrittenAsAJSONEscapeInsideAStringHoldingJSONText`). No #208 test through `Redact` on plain text changed.
- **`removed()`** (the predicate of `Text`) decides ASCII in a short branch before the Unicode tables; `Redact` of 64 KiB of mostly-ASCII non-ASCII text went from 1.13 ms to 0.46 ms, ASCII unchanged. A side effect, not a goal.
- **Out of scope per the ticket, pinned and tracked:** the audit line's operation ID is cleaned by `sanitize.Text` before the redactor reads it, so `x<ZWSP>sk-lf-…` is shown glued in the audit line while the tool error is redacted (`TestAKeyAfterAHiddenCharacterInAnOperationIDIsRedactedInTheToolErrorAndShownInTheAuditLine`). Documented in the three docs; evidence and a one-line fix (`sanitize.Text(r.Redact(...))`) added to #211 as a comment, no new issue.
- Not run (outside a ticket): `/security-review`, `/e2e-campaign`, integration tests against a real Langfuse (the ticket's "Not checked").

## Learnings
- The tool harness turns a typed backslash-u + 4 hex digits (and some `\ufffd`, `\u00e9`) in file contents into the real character. Build such text from pieces (`` `\` + "u" + hex ``, `string(rune(0x200b))`) and `grep -nP '[^\x00-\x7F]'` the new files.
- Never `rm -rf internal/sanitize/testdata/fuzz` to clean up replayed fuzz corpus: it holds a tracked seed (restored with `git checkout`). Copy cached corpus files to a scratch directory instead.
- `go test -fuzz` printing `0/sec` for tens of seconds is the engine (minimization/sync), not a slow input: replaying the whole cached corpus took 0.04 s.
- `strings.Map` with a closure that calls a non-inlinable predicate per rune doubled the time of `Text` on non-ASCII text; deciding ASCII in a small inlined-friendly branch first halved it. Measure with alternating base/new test binaries (`go test -c`), not back-to-back runs.
