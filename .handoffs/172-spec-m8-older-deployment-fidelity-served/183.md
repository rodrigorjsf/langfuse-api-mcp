## What was built
- On a deployment whose Langfuse version does not serve `traceId` of `scores_get-many` (from 3.133.0) or `level` of `legacy_observationsV1_getMany` (from 3.82.0), `execute_read` with that filter no longer gets the "not served" refusal. The server reads the list without the filter, page by page from page 1 at 100 rows a page, keeps the rows whose `traceId` / `level` equals the value, and stops at the end of the list or after 10 pages.
- The result is page-shaped: matching rows in `data`, and a static summary in `meta.filterScan` (`appliedBy: "server"`, `parameter`, `rowField`, `complete`, `pagesRead`, `rowsRead`, `rowsExist`, `rowsMatched`). None of Langfuse's own pagination metadata is passed through. A scan that stopped at 10 pages is `complete: false` and carries a fixed hint.
- `page` with a scanned filter is `invalid_argument` (hint: call again without `page`). A failed page ends the scan with its tool error and no rows. Where the version serves the filter (or is undetected) the call is one ordinary request, unchanged.
- Verified live on the pinned 3.80.0 stack: scores of one trace, ERROR observations, and the refusal of a still-unserved parameter.

## Decisions & deviations
- The scan loop lives in `internal/workflows/filterscan.go` (placement table: a multi-call read flow). Workflows may not import catalog (depguard), so `catalog.Operation.Scan` returns the plan (`catalog.Scan`) and the server passes plain fields to `workflows.FilterScan`.
- `Operation.Scan` validates the call as if the deployment served the filter (a copy of the operation with the parameter moved into `Params`, then `Request`), so the scanned value gets exactly the checks of a sent one and the other parameters are checked and sent as usual. The filter is then removed from the query and `limit` set to `MaxLimit`.
- A caller's `limit` is checked, then replaced by 100 (the ticket says the scan reads "at the page size maximum" and the other parameters "unchanged"; a page size is the scan's own). `page` is refused (JSON null `page` counts as absent). A JSON null filter is no filter and falls to the ordinary path (still refused as not served, as before).
- End of list: `meta.totalPages` decides; without it only an empty page proves the end (a short page may only be a smaller page size, so "complete" on it could present a partial answer as complete). `rowsExist` is Langfuse's `totalItems`; without it, the rows read when complete, omitted otherwise (the hint says "of how many exist when Langfuse counts them").
- Rows are compared after `sanitize.Payload` with the redactor, the value as sent: a value holding a Langfuse key or bearer token matches nothing (no leak). Documented in tools.md and security.md, test `TestAScannedValueThatHoldsAKeyMatchesNothingAndTheKeyComesBackNowhere`.
- The final payload is encoded without a second `sanitize.Payload` pass (rows were already cleaned; the summary is static), HTML not escaped as everywhere else.
- Added `sanitize.WrapNoted` (envelope with a fixed note after the truncation hint) so the incomplete-scan hint survives clipping; the scan overrides the operation's remedies (no lower `limit`, no paging).
- `execute_read`'s static description now names the scan (review finding; it also narrows #199 to `describe_operation`).
- #173's tests that asserted the refusal of `scores_get-many` `traceId` on 3.80.0 (server `served_test.go`, live `served_integration_test.go`) now use `sessionId` (served from 3.112.0, not scanned): the behaviour changed by design. `describe_operation` keeps listing only served parameters, as #173 requires.
- Integration seeding uses the ingestion batch directly (test code only, not a server tool). 3.80.0 cannot delete observations, so the `level` live test leaves two on the throwaway stack.

## Learnings
- `go test -race ./internal/server` needs more than 6 GB RSS (even the base commit); on a 7.9 GB WSL machine run it in chunks with an RSS guard: `go test -race -c`, `server.test -test.list .`, then `-test.run '^(a|b|…)$'` per chunk (≤3.1 GB each). `GOGC`, `GOMEMLIMIT` and `-test.parallel` did not lower it.
- `pkill -f server.test` / `pgrep -f` match the shell running them; kill by PID.
- `gofmt` is not on the bash PATH: `$(go env GOROOT)/bin/gofmt`.
- A background `go test` hung at 22 minutes shows only goroutine 0 in the dump; read RSS (`ps -eo pid,rss,comm`) before suspecting a deadlock.
- A sed mutation that does not match changes nothing and looks like a vacuous test: grep the file for the change before reading the result.
- Test params must be `float64`/`json.Number`, not Go `int`, when calling `Operation.Request` or `Scan` directly.
