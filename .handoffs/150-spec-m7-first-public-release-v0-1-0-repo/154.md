## Decisions & deviations
- **Offline validation.** `mcp-publisher validate` (v1.8.1) calls the live Registry (verified locally: "Validating against https://registry.modelcontextprotocol.io..."). Using it in the snapshot job, which also gates the tag, would let a Registry outage block a release. So I vendored the published schema and validate with `google/jsonschema-go`, which the module already depends on. `go.md` now allows that use.
- **Template location.** server.json lives in `packaging/` (release inputs), and the renderer in `scripts/` as a Go program, like `gen-os-test-ca`.
- **When the `.mcpb` is listed.** "Part of the release" is decided from the GitHub release's assets at publish time. Today `github-release` always attaches the `.mcpb`, so the entry will list it. Gating the MCPB on #129 is the release ticket's job (#158): drop `*.mcpb` from the release, and the Registry entry follows automatically.
- **Release environment.** `publish-registry` runs in the `release` environment. The Standards review asked for it, to match security.md "publish jobs run in the release environment". It needs no secret.
- **First release.** The Registry verifies OCI ownership by reading the image label, which it cannot do while the GHCR package is private. On the first release the job is expected to fail until README step 7 makes the package public, then it is re-run. This is documented in README step 6.
- **OCI env variables.** The OCI package does not list `LANGFUSE_CA_CERT`, because it needs a mount, not just a variable.
- **Test order.** The workflow tests were written after the job, so no red came first. Red was proven afterwards by flipping `continue-on-error` to false: 1 failure.

## Learnings
- `mcp-publisher validate` is not offline: it POSTs to the live Registry. Validate against the vendored schema instead.
- The MCP Registry checks OCI ownership through the image label, so the first publish fails while the GHCR package is private.
